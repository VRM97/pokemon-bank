# Pokémon Bank API

```lua
local bank = mod.find("vrm_pokemon_bank")
if bank then
  local boxNum, slot = bank.exports.depositPokemon(mon, { game = game })
  local mon2 = bank.exports.withdrawPokemon(boxNum, slot, game)
end
```

`mod.find` returns `nil` when Pokémon Bank isn't installed or is disabled -- always check the handle before calling into `.exports`. Nothing here depends on any particular save/version being active; the Bank's storage is shared across all of them (see README.md's **Where the data lives**).

`listBoxes()` returns the Bank boxes in display order. Each entry contains the box's stable `id` and its optional `name`.

## Box numbering: read this before storing a `{ box, index }` pair

A box's **number is a snapshot, not a stable id**. By default, the instant a box empties out (its last Pokémon withdrawn, released, or moved away) and it has no name, that box is deleted outright rather than kept as a hole, and every later box's number shifts down by one to fill the space -- a box's own name (see **Persistence** below) shifts down right along with it. The player's own **DELETE EMPTY BOX** option controls this: **UNNAMED** (the default, described above) leaves a *named* empty box in place instead of deleting it, **ALL** deletes every empty box regardless of name (dropping its name too), **NEVER** deletes none automatically -- MANAGE BOX's own **DELETE** action is the manual equivalent for a box a policy of UNNAMED/NEVER would otherwise keep, but only ever on an already-empty box. `boxCount()` is always `(occupied or kept-empty boxes) + 1` -- the `+1` is the one spare empty box every call that can grow the Bank (`depositPokemon`, `movePokemon`) is guaranteed to find room in. MANAGE BOX's own **SWITCH** is the one deliberate exception to the numbering itself: it swaps two box numbers' contents and names outright, on the player's own request.

Practically: don't cache a `{ box, index }` pair across a turn boundary, an event, or any other mod's own deposit/withdraw and expect it to still point at the same Pokémon -- re-resolve it from `listPokemon()` first, or call `getPokemon(box, index)` and compare against what you expect to find there before acting on it (`withdrawPokemon`/`releasePokemon` on a stale pair just does nothing useful -- whatever is actually sitting in that slot by then). This mod's own UI follows the same rule internally.

## Pokémon

**Identity fields.** Validation gives every stored mon three fields, all kept as plain numbers/strings on the mon so they travel with it: `otSecretId` (the Secret ID of its original trainer), `personality` (a Gen 3 style 32-bit personality value, the mon's identity inside the Bank; it replaced `bankId`, which is removed from any mon that still has one) and `speciesAlt` (its species in the *other* form: the internal number next to a text id, or the text id next to a number, so `reshapeForActiveGame` only swaps them). A mon with no `otSecretId`, or a 0, gets the current trainer's when its `originGame` and OT name are the current game's and trainer's, otherwise 0. A mon with no `personality` gets a rolled one that keeps its gender and shininess (and, for an Unown, its letter) and is drawn together with the IVs its DVs become on Gen 3: Gen 3 makes a mon's PID and IVs from consecutive outputs of one random generator (methods 1, 2 and 4), so a given set of IVs only fits about fifteen PIDs, found with PKHeX's seed-recovery algorithm (`LCRNGReversal`/`LCRNGReversalSkip`), and one of those that keeps the rest is picked. A shiny is the exception (about one in 8192 of those is shiny), as is any mon for which none of them fits: those get a PID that keeps their traits without the correlation, and are marked `mon.pidIvExempt` (`"shiny"`, or `"unmatched"`; the red GYARADOS of the LAKE OF RAGE caught on Gen 2 gets `"event"`) so that LEGALITY CHECKS on Gen 3 leaves the correlation alone for them. A mon met in Gen 3 is never marked. The trainer's own SID is created first, when the save has none (see **Trainer IDs** below).

Every deposit stamps `mon.originGame` and `mon.originGeneration` the first time that mon enters the Bank. Only set when still `nil`, so a later re-deposit (from a different save or version) never overwrites them. A mon banked before these fields existed carries neither -- `validatePokemonStorage` backfills them for one still missing either, but only when `mon.otId` matches the validating save's own trainer id.

- `depositPokemon(mon, opts)` -- `opts.game`, if given, freezes the mon's stats block before storage and stores its species in both forms (`speciesAlt`). There is no box limit. Returns `boxNum, slotIndex`, or `nil, "invalid pokemon"` for a malformed `mon`.
- `depositPartyPokemon(game, opts)` -- bulk deposit from the player's party to the Bank. `game` is required. `opts.boxNum` specifies the target Bank box (defaults to the last box, which is always empty). `opts.indices` is an array of party indices to deposit (defaults to `2..last`, keeping the first Pokémon). Returns an array of `{ box, index, mon }` for each deposited mon, or `nil, "error message"`. Ensures at least one Pokémon remains in the party. When a box fills, remaining mons continue to the next box.
- `depositBoxPokemon(game, pcBoxNum, opts)` -- bulk deposit from a PC box to the Bank. `game` is required. `pcBoxNum` is the source PC box number (1-12 on Gen 1/2, 1-14 on Gen 3). `opts.boxNum` specifies the target Bank box (defaults to the last box). `opts.indices` is an array of PC box slot indices to deposit (defaults to every occupied slot; an empty slot is an invalid index). On Gen 3 the slots left behind stay empty instead of closing up. Returns an array of `{ box, index, mon }` for each deposited mon, or `nil, "error message"`. When a box fills, remaining mons continue to the next box.
- `withdrawPokemon(boxNum, index, game, fix)` -- removes and returns the mon table, or `nil` if that slot is empty (see box-numbering caveat above), or `nil, "generation"` when the mon carries a TIME CAPSULE floor (`mon.minGeneration`, see **TIME CAPSULE** below) the active generation doesn't clear, or `nil, "illegal"` when **LEGALITY CHECKS** refuses the mon -- checked on the mon still in its box, so a refusal never removes it first. `game` is optional but strongly recommended: when given, catches the mon in the Pokédex (`seen` + `owned`/`caught`) if it wasn't already -- withdrawing is the only Bank action that can land a mon somewhere new (the party or a PC box), so it's the one that can introduce a species the Pokédex hasn't recorded yet. Without `game`, the withdrawal still happens; only the Pokédex write is skipped. `fix` (default `false`) only matters under **LEGALITY CHECKS**' own **FIX** choice: `true` lets `tryFixLegality` (below) actually correct the mon in place instead of just refusing it, same as **REJECT** would; this mod's own screens ask the player first (see README's own **LEGALITY CHECKS** section) -- a caller that wants the same confirmation has to ask before passing `true` itself, since this stays a plain synchronous call with no dialog of its own. Under **FORCE FIX**, `fix` is ignored entirely -- a failing mon is always corrected in place, the same way it would be had the caller passed `true` under **FIX**.
- `withdrawToParty(game, opts)` -- bulk withdraw from the Bank to the player's party. `game` is required. `opts.boxNum` specifies the source Bank box (defaults to the first non-empty box). `opts.indices` is an array of Bank slot indices to withdraw (defaults to all). `opts.fix` is `withdrawPokemon`'s own `fix` (above), applied to every mon in the batch. Returns `{ withdrawn = [array of { mon }], remaining = count }`, or `nil, "error message"`. Withdraws up to the party's capacity (6 total); any remaining mons stay in the Bank, same as one refused by the TIME CAPSULE floor or **LEGALITY CHECKS** (see `withdrawPokemon` above) -- all three are silently skipped rather than reported individually.
- `withdrawToBox(game, targetPcBoxNum, opts)` -- bulk withdraw from the Bank to a PC box. `game` is required. `targetPcBoxNum` is the destination PC box number (1-12 on Gen 1/2, 1-14 on Gen 3). The mon takes the first empty slot. `opts.boxNum` specifies the source Bank box (defaults to the first non-empty box). `opts.indices` is an array of Bank slot indices to withdraw (defaults to all). `opts.fix` is `withdrawPokemon`'s own `fix` (above), applied to every mon in the batch. Returns `{ withdrawn = [array of { mon, pcBox }], remaining = count }`, or `nil, "error message"`. Fills the target box first, then overflows to subsequent PC boxes; if all PC boxes are full, the TIME CAPSULE floor refuses a mon, or **LEGALITY CHECKS** refuses one, it stays in the Bank the same way.
- `getPokemon(boxNum, index)` -- read-only peek; does not remove.
- `getBox(boxNum)` -- a snapshot copy of one box's slots, indexed `1..boxCapacity()` (`nil` for an empty slot), for a mod that wants to render the Bank as a grid instead of walking `listPokemon()` itself. With **BOX SIZE** at **NO LIMIT** (`boxCapacity()` returns `math.huge`), there's no fixed grid to pad out to -- the copy is exactly as long as the box actually is instead. A copy, not a live reference -- mutating it does nothing to the Bank; call it again after any mutation to see the result. `nil` for a `boxNum` outside `1..boxCount()`.
- `movePokemon(srcBox, srcIdx, destBox, destIdx)` -- relocates within the Bank; landing on an occupied slot swaps the two, landing on an empty slot appends to the destination box (same "all empty grid cells are equivalent, boxes are dense arrays" convention the vanilla PC uses). Returns `true`, or `false` (`"full"` if the destination box is already at `boxCapacity()`).
- `releasePokemon(boxNum, index)` -- removes it for good; returns whether anything was actually there to remove. No confirmation -- this mod's own UI asks first, but the exported call does not.
- `listPokemon()` -- every stored mon, as a flat array of `{ box, index, mon }`.
- `pokemonCount()` -- total Pokémon across every box.
- `isValidPokemon(mon, game)` -- `true` when the mon's text species id (`mon.species`, or `mon.speciesAlt` while `species` holds the number) exists in `game.data.pokemon` (and it isn't an Egg on a Gen 1 save without CRYSTAL_251 or Kanto-Reforged). Exported so other mods can reuse the same rule before depositing or when building their own Bank UI.
- `isLegal(mon, game)` -- (on Gen 3 it runs its own set of checks, listed in README.md's **LEGALITY CHECKS**, against the engine's numeric species and moves)  the check behind **LEGALITY CHECKS** (**OFF** by default), ported from PKHeX's Gen1/Gen2 legality checks (source-pkhex/) but re-targeted at this recreation's own extracted game data instead of PKHeX's own tables -- see README.md's **LEGALITY CHECKS** for exactly what's checked and what's deliberately left out (timing/encounter legality, trade evolutions). Expects `mon` already shaped for `game` -- see `reshapeForActiveGame` below for where that happens -- rather than reshaping it itself. Returns `true`, or `false, reason` (a short string, for debugging -- `withdrawPokemon`/`withdrawToParty`/`withdrawToBox` only look at the first value). `withdrawPokemon`/`withdrawToParty`/`withdrawToBox` only call it at all while the option isn't **OFF**; exported so another mod can run the same check itself regardless of the option.
- `tryFixLegality(mon, game)` -- attempts to correct an illegal `mon` in place for **LEGALITY CHECKS**' own **FIX** choice: recomputes the level off exp, clamps DVs/Stat Exp back into range (rederiving the HP DV and, on Gen 2, the combined Stat Exp cap), drops any duplicate/unlearnable move and truncates down to 4, resets an out-of-line catch rate, rederives Gen 2's gender/shininess off their own DVs, and strips a held item that can't legitimately be held. Runs `isLegal` first and returns `true` immediately if `mon` already passes; otherwise snapshots it, applies the above, and either leaves it fixed (returns `true`) or restores it exactly as it was and returns `false, reason` -- `mon` is only ever left mutated when the result is `true` (already legal or now fixed), never on a `false`. Some failures have nothing to converge on at all (an unknown species, an Egg's own species/game-support gate, or a moveset that empties out entirely) and are refused immediately without attempting anything. Exported so another mod can offer the same fix (see this mod's own README for why its own screens ask the player first, and API.md's own `withdrawPokemon` entry for the exported withdraw calls' own `fix` parameter).
- `needsLegalityFix(mon, game)` -- `true` only when **LEGALITY CHECKS** is on **FIX** and `mon` currently fails `isLegal` -- `false` under **OFF**/**FORCE FIX**/**REJECT**: **FORCE FIX** corrects a failing mon itself without asking, and **OFF**/**REJECT** never offer to fix anything at all. For a caller that wants to ask the player before calling `tryFixLegality` (or passing `fix = true` into a withdraw call), the same way this mod's own screens do.
- `validatePokemonStorage(game)` -- scans `boxes` and `orphaned.mons` bidirectionally: invalid mons in `boxes` move to `orphaned.mons`, mons in `orphaned.mons` that are now valid append to the last box in `boxes`. Every mon that stays (or lands back) in `boxes` is also run through `reshapeForActiveGame` right there -- the one place a Bank mon gets shaped for `game`, done once per `save.loaded` rather than again at every later withdraw/STATS/transfer. Also strips an invalid or blacklisted held item off any mon that otherwise stays valid (into the same item quarantine `validateItemsStorage` uses), backfills a still-valid mon's missing `originGame`/`originGeneration` when its `otId` matches the current trainer's TID (see **Pokémon** above), makes sure the trainer has an SID, gives every mon in either list its `otSecretId` and `personality` (see **Identity fields** above; moves set aside under an old `bankId` follow the mon to its `personality`), and runs the move-only quarantine pass described below. Returns `{ changed, quarantined, restored, lostMons, restoredMons, lostItems }` (`lostItems` is the held-item stripping above, `{ id, count }` shaped same as `validateItemsStorage`'s own). Marks the Bank dirty itself whenever it reshapes a mon; `validateStorage` (below) still handles the combined dirty flag for everything else this scans.
- `validateTimeCapsuleStorage(game)` -- the same bidirectional pass as `validatePokemonStorage`, but between `timeCapsule` and `orphaned.timeCapsule` (see **Time Capsule** below); no held-item or move scrubbing, since a capsule Pokémon only gets those checks at the moment it's actually withdrawn. Reshapes every mon that stays (or lands back) in `timeCapsule`, same as `validatePokemonStorage`. Returns `{ changed, quarantined, restored, lostMons, restoredMons }`.
- `listInvalidPokemon()` -- every quarantined mon as `{ index, mon }` (a copy of the list; mutating it does nothing to the Bank).
- `invalidPokemonCount()` -- how many mons are in `orphaned.mons`.
- `listInvalidTimeCapsulePokemon()` / `invalidTimeCapsulePokemonCount()` -- the same two, over `orphaned.timeCapsule` instead (see **Time Capsule** below).
- `boxCount()` -- see **Box numbering** above.
- `boxCapacity()` -- slots per box: `getBoxSizeOverride()` when set, otherwise the player's own **BOX SIZE** option (**20**/**30**), or `math.huge` at **NO LIMIT** either way, rather than a magic sentinel -- a plain `#box < boxCapacity()` check works regardless of which one is deciding it. Shrinking it doesn't truncate anything: whatever no longer fits in a box moves to the tail, filling whatever box is currently last and then a fresh one after that, the same rule any deposit already follows.
- `setBoxSizeOverride(value)` -- forces `boxCapacity()` straight past the player's own **BOX SIZE** option: a positive integer for that many slots, `math.huge` for no limit, or `nil` to clear the override and hand the decision back to the option (the default). Takes effect immediately, including the reflow above if it shrinks the effective capacity. Lives only in memory, same as `blacklistItem`. Returns `true`, or `false, "bad request"` for anything else (`0`, a negative number, a fraction).
- `getBoxSizeOverride()` -- the raw override itself (a number, `math.huge`, or `nil`), not `boxCapacity()`'s already-combined effective value -- same reason `getTmItemDepositOverride()` exists below: a caller that wants to force it one way and then put back exactly what was there before.
- `reshapeForActiveGame(game, mon)` -- the cross-generation backfill for a mon that just cleared validation: collapses `exp`/`experience` down to whichever one the active generation reads (never both), translates `status` between Gen 1 and Gen 2 (Gen 2's `toxic` degrades to plain `PSN` on Gen 1, which has no separate badly-poisoned status; the Gen 2-only `statusTurns`/`toxicCounter` are dropped when heading to Gen 1), collapses CRYSTAL_251's `heldItem`/Gen 2's `item` and Gen 2's `eggSteps`/CRYSTAL_251's `eggCycles` the same way, reshapes Egg moves between `moves`/`eggMoves`, reshapes `moves[i].ppUps`/`maxPp` (see `reshapeMoves` below), and splits/recomputes `stats.specialAttack`/`specialDefense`, backfills `maxHp`/`types`/`catchRate` from `game.data.pokemon`, rolls a `gender` from the Attack DV/`genderRatio` rule when the mon doesn't have one yet (a Gen 1 mon never does), and defaults `happiness`/`pokerus` to `70`/`0` (the same starting values `src.battle.gen2.Mon` itself uses) when the mon doesn't have them yet and the active game actually tracks them -- always on Gen 2, only on Gen 1 with CRYSTAL_251 installed (`heldItem`/`eggCycles` above are its doing too). Left untouched on plain Gen 1: nothing there reads either field. Mutates and returns `mon`. This mod calls it in exactly two places, both right after a mon has already been validated rather than at every later touch: `validatePokemonStorage`/`validateTimeCapsuleStorage` (so every mon already sitting in the Bank is shaped once per `save.loaded`), and LINK's own receive step, between the SEND and RECEIVE stages, right after a mon clears `isValidPokemon` there. A mod that moves a Pokémon between generations on its own path (bypassing both) can still call this first to get the same treatment instead of reimplementing it.
  It also makes `mon.species` the form the active game reads (the text id on Gen 1/2, the internal number on Gen 3, swapping with `speciesAlt`). It also converts the mon's moves between the two layouts: `moves` is what the active game reads (entries `{ id, pp, ppUps | maxPp }` on Gen 1/2; plain move numbers on Gen 3, with `pp` and `maxPp` as parallel arrays) and `movesAlt` holds the ids of those moves in the other form (numbers next to entries, text ids next to numbers; `false` where there is none), rebuilt every time the mon is deposited with a `game` (a deposit without one drops it; one that no longer lines up with `moves` is rebuilt from the mon's own moves). Moves cross generations **by name, never by index** (a mod's own move can reuse another generation's index), and always on the side that can read FireRed's own tables -- FireRed itself, since the engine refuses a mod its `src.*.game3.*` modules on a Gen 1/2 game. Going into FireRed, each move's Gen 1/2 id, spelled the Gen 3 way (`translateMoveId`, a table compared by hand against every generation's move list and Kanto-Reforged's), is looked up there (`movesAlt` only when the name isn't found). Coming out of FireRed, `movesAlt` -- the Gen 1/2 ids worked out by name when the mon was deposited on FireRed -- is swapped in, and the Gen 1/2 game only checks each move is one it has. A Gen 1/2 game never guesses a FireRed number or name. `movesAltOf` records the moves `movesAlt` was worked out for: once the mon's moves change (the Bank's own RELEARN MOVES or TMs, another mod, the game's move-learning screen), `movesAlt` is worked out again by name on FireRed and dropped on Gen 1/2 -- right away where the Bank changes them, on the next validation or change of generation otherwise. A mod that changes a mon's moves itself can call `movesChanged(game, mon)` (true when it changed anything) to do it at once. Species work the same way: 1-251 are the same number everywhere; a Hoenn species gets its FireRed number on FireRed, and its text id back from `speciesAlt`. PP and PP Ups are converted on the way. A move the target doesn't have (a Gen 3 move on Gen 1/2, a later-generation move from Kanto-Reforged on FireRed, a Gen 2 move on Gen 1, a FireRed number FireRed doesn't have) is set aside under the mon's `personality` (RELEARN MOVES) instead of being lost; between Gen 1 and Gen 2 a move the target spells differently is kept, renamed. It also translates `status` to Gen 3's codes (`SLP`/`PSN`/`TOX`/`BRN`/`FRZ`/`PAR`, with the sleep turns in `mon.sleep`; `TOX` becomes `toxic` on Gen 2 and `PSN` on Gen 1), spells `gender` as `M`/`F`/`U` on Gen 3 and `male`/`female`/`unknown` on Gen 2, and keeps an Egg's hatch counter where each game reads it (`eggSteps` on Gen 2, `eggCycles` on Gen 1, `eggCycles` plus `friendship` and the `egg` flag on Gen 3). On Gen 3 it also fills what is missing of `nature` (from `personality`), `ability`/`abilityId`, `growthRate`, `friendship`/`happiness` (70 when neither exists), `pokerus` (0), `metLevel` (the current level, 0 for an Egg), `pokeball` (a POKé BALL), `metLocation` (255, the Gen 3 "fateful encounter" location) and `fatefulEncounter` (false), and never overwrites a value that is already there; `ivs` (`hp`/`atk`/`def`/`spe`/`spa`/`spd`, 0-31) come from the mon's `dvs` when it has none: each DV is limited to 0-15 and then gets one bit added (`iv = dv * 2 + 1`, so 15 becomes 31), Special feeds both Special IVs, and the HP DV is the low bits of the other four. Going back to Gen 1/2 a mon with `ivs` and no `dvs` gets them: each IV is limited to 0-31 and loses its low bit (`dv = floor(iv / 2)`), Special takes Special Attack's, and the HP DV is rebuilt from the bits of the rest. Nothing is rolled. The set the active game doesn't use is then deleted (no `dvs` on Gen 3, no `ivs` on Gen 1/2), and the one the mon already has is never replaced by a conversion. `evs` and `statExp` work the same way: `statExp` (limited to 0-65535) loses its low byte to become EVs, and EVs (limited to 0-255) get a byte of ones added (`stat exp = ev * 256 + 255`, so 255 becomes 65535); Special takes Special Attack's. The caps (510 EVs in total, Gen 2's 65535 Stat Exp in total) are not applied. On Gen 1/2 a capture (the `pokemon.caught` event) records `metLevel`, `metLocation` (255) and `pokeball` (the ball's item id) on the caught mon; `pokeball` is swapped with `pokeballAlt` (the Gen 3 item number, or the original id of a ball Gen 3 doesn't have, which is a POKé BALL there) when the mon crosses. These fields stay on the mon when it goes back to Gen 1/2. Stats are calculated again whenever a mon crosses the Gen 3 boundary, never converted from the ones it already has: entering Gen 3 they are calculated from its IVs, EVs, level and PID and stored flat (`maxHp`, `attack`, `defense`, `speed`, `spAtk`, `spDef` and the `atk`/`def`/`spe`/`spa`/`spd` aliases, with no `stats` table); leaving it they are calculated from its DVs and Stat Exp into a `stats` table (plus `maxHp` on Gen 2) and the flat fields are deleted. The mon keeps its share of HP (current over maximum, when it has both; a mon that is alive stays at 1 HP at least, a fainted one stays fainted); with no share its HP is the new maximum. A Gen 3 mon that already has flat stats keeps them on Gen 3. Gen 1 and Gen 2 are not recalculated between themselves.
- `reshapeMoves(game, mon)` -- just the move-PP piece of the above, in case a mod only needs that: Gen 1 keeps a move's bonus PP on `ppUps` and recomputes the cap on every read, Gen 2 stores the raised cap directly on `maxPp` and keeps no `ppUps` counter; this fills in whichever field the active generation expects from whichever one the mon already carries. Mutates `mon.moves` in place; returns nothing.
- `reshapeStatus(mon)` -- just the status piece of the above, in case a mod only needs that: translates `mon.status` between Gen 1's `SLP`/`PSN`/`BRN`/`FRZ`/`PAR` and Gen 2's `sleep`/`poison`/`burn`/`freeze`/`paralyze` (Gen 2's `toxic` degrades to plain `PSN` on Gen 1; the Gen 2-only `statusTurns`/`toxicCounter` are dropped when heading to Gen 1). Takes no `game` -- it only needs `GameVersion.generation()`. A no-op when `mon.status` is already `nil`. Mutates `mon` in place; returns nothing.
- `healBank(game)` -- heals every Pokémon currently stored in the Bank in place: full HP, status cleared, every move's PP restored to its current-generation cap. `game` is required. Returns how many mons were healed; marks the Bank dirty when it healed at least one. This is what the **AUTO HEAL** option's **AT POKéMON CENTER** choice calls.
- `registerDex(game, species)` -- marks `species` seen and owned/caught in `game`'s own Pokédex (whichever field name the active generation uses). A no-op without a Pokédex on the save. Exported so a mod that lands a Pokémon in the player's game some other way (TIME CAPSULE below is the one built-in caller besides `withdrawPokemon`/etc themselves) can mark it the same way a normal withdraw already does.

**Trainer IDs.** The TID is always the game's own: every engine rolls one for a new game (`save.player.id` on Gen 1/2, the session's `trainerId` on Gen 3), and the Bank never generates it. Before validating, `validatePokemonStorage` makes sure the loaded save's trainer has an SID, rolling a 16-bit number (the Gen 3 rule) when missing (FireRed already has its own); the SID is set on the same table as `secretId` and also kept in this save's mod data (`secret_id`), since a save that only stores what its own game knows would drop it.

## TIME CAPSULE

Its own top-level tab on the BANK menu, right below POKéMON, gated by its own **TIME CAPSULE MENU** SHOW/HIDE toggle (see **PC menu entry** below) exactly like POKéMON/ITEMS/MOVES/MONEY/LINK are gated by their own toggles -- turning it off doesn't touch MANAGE PKMN or MANAGE BOX, and turning POKéMON off doesn't touch TIME CAPSULE. TIME CAPSULE lives in the Bank's own `storage.lua` as `entries.timeCapsule` -- a flat list of Pokémon with no boxes, since nothing about it needs them. `validateTimeCapsuleStorage` (see **Pokémon** above) quarantines one the currently loaded game no longer recognizes into `s.orphaned.timeCapsule`, the same way `validatePokemonStorage` does for `boxes`/`orphaned.mons`, and the main `validateStorage` pass runs it on every load. Simulates the real Gen 1 -> Gen 2 Time Capsule one-way: a Pokémon deposited from an earlier generation's save can only ever be withdrawn into a **later** one, never back down, and only the one direction this project currently has two generations for is possible at all (Gen 1 -> Gen 2).

That "later" comparison is `mon.minGeneration` -- **not** the highest generation a Pokémon has reached, but the lowest one it's still allowed to withdraw INTO (a floor, not a ceiling). TIME CAPSULE deposit sets it to the depositing save's own generation **plus one** (there's nothing to check yet -- the trip hasn't happened); a successful withdraw then sets it to the destination's own generation, so a further hop (once this project has a Gen 3) has to clear that new floor in turn. Withdrawing is refused whenever the *current* generation is less than this field. It's untouched by the general Bank's own, deliberately unrestricted, cross-generation storage, so it survives a Pokémon drifting back into an earlier-generation save through `depositPokemon`/`withdrawPokemon` -- a re-deposit into TIME CAPSULE from that earlier save still sets the same floor it would have the first time, since the depositing generation hasn't changed. The floor is also enforced on that general Bank side: `withdrawPokemon`/`withdrawToParty`/`withdrawToBox` (see **Pokémon** above) refuse a mon whose `minGeneration` the active generation doesn't clear, the same way TIME CAPSULE's own withdraw does -- otherwise MANAGE PKMN would be a free bypass for the exact same restriction.

The player's own **LEGALITY CHECKS** option (see below) gates TIME CAPSULE too, on both ends: a Pokémon that couldn't legitimately withdraw straight into a game (`isLegal`, below) is refused at TIME CAPSULE deposit as well as withdraw, on top of every generation/species/move/held-item check that always applies regardless of the option. On **FIX**/**FORCE FIX**, only the withdraw side offers to correct it (**FIX** after asking, **FORCE FIX** immediately -- see below) -- deposit still just refuses it outright, same as **REJECT**.

- `openTimeCapsuleMenu(game)` -- pushes the TIME CAPSULE screen directly, no top-level BANK chooser required (same convention `openPokemonMenu`/etc already follow for **SHOW IN PC MENU**). Works regardless of the current **TIME CAPSULE MENU** toggle, same as `openPokemonMenu`/etc bypass their own tab's SHOW/HIDE. Returns whatever `mod.ui.push` returns, or `nil, "no game"` without one.
- `timeCapsuleScreenId` -- the registered screen id (`mod.content.screens`) behind that screen, for a mod that wants to push it through its own navigation.
- `isTimeCapsuleTabEnabled()` / `setTimeCapsuleTabEnabled(enabled)` -- the read/write pair for the player's own **TIME CAPSULE MENU** option, same shape and same combination rule as `isPokemonTabEnabled`/`setPokemonTabEnabled`/etc (see **PC menu entry** below). Replaces the old `isTimeCapsuleEnabled()`, which read the now-removed **STORAGE MODE** option instead.
- `timeCapsulePokemonCount()` -- how many Pokémon are currently sitting in the capsule.
- `listTimeCapsulePokemon()` -- every one of them, as a flat array of `{ index, mon }` (a copy; mutating it does nothing to the capsule).

The screen (`entry.screen` shape, see **Screens** below) is a plain 4-container `Screen.entryScreen`: **TIME CAPSULE**, **BANK**, **PARTY**, **PC** -- SELECT cycles between them, same as MANAGE PKMN. BANK/PARTY/PC reuse the exact same containers MANAGE PKMN itself uses (`Pokemon.containers`, same box/party/PC content, same views), stripped of MOVE/MANAGE BOX (out of scope here) and given one onAction row of their own, **TO TIME CAPSULE** (plus **STATS**): refuses a Pokémon that's an Egg or holds an item, refuses *everything* while the currently active game is already at this project's highest supported generation (nowhere further for anything to go from there, regardless of any one Pokémon's own `mon.minGeneration`), or fails `isLegal` while **LEGALITY CHECKS** isn't **OFF** -- no bulk TRANSFER on these three here, same as the old DEPOSIT PKMN was always one Pokémon at a time.

The **TIME CAPSULE** container lists the capsule's own flat contents; picking one offers **TO BANK**/**TO PARTY**/**TO PC** (**TO BANK** hidden while the player's own **POKéMON MENU** tab is off, since there'd be nowhere for it to land), **STATS** and **RELEASE** -- no **MOVE**, there's nothing to reorder into, the capsule has no boxes. **TO PC**/**TO BANK** land in whichever PC/Bank box that container is currently showing in this same screen (`env.pageOf`, same convention MANAGE PKMN's own cross-container moves already use), not a separately-tracked "current box". `canTransfer` gives it a bulk **TRANSFER** row on START too, collapsing to a direct move or a **TO BANK**/**TO PARTY**/**TO PC** submenu exactly like MANAGE PKMN's own bulk moves -- it moves every Pokémon currently visible in the capsule at once; one that isn't eligible yet (generation floor) or needs **LEGALITY CHECKS**' **FIX** confirmation is simply skipped (refused, not asked about) rather than prompting per mon, same precedent boxes' own bulk TRANSFER already set. **RELEASE** fires `pokemon_released` (below) same as any other release, with `box = nil` since the capsule has none. A Pokémon that clears the generation floor has its species and every one of its moves translated to the destination's own ids (`translateSpeciesId`/`translateMoveId` below) **whether or not** a later check in that same pass still refuses it -- `isLegal` needs them translated to look anything up at all, and this mirrors how `isLegal` itself already reshapes a Pokémon it ends up refusing (see its own entry above). The translated species must exist in the destination's own data, every move must be `canLearn`-legal there, and `isLegal` itself must pass unless **LEGALITY CHECKS** is **OFF**; on **FIX**, a Pokémon `isLegal` refuses is offered a fix instead of an outright refusal (per-row only, asked once for that one Pokémon) -- and only actually leaves the capsule once `tryFixLegality` (above) confirms it. Any refusal (including a declined or failed fix) leaves the Pokémon in the capsule, already translated. One that clears everything and doesn't already hold an item is stamped with one deterministically on deposit and applies it on withdrawal, mirroring the real cart's own Gen1->Gen2 quirk: the species' Gen 1 catch rate byte is reused as a Gen 2 item index (`mon.timeCapsuleItemByte`, resolved at withdrawal against the destination's own `game.data.items[id].index`), with a fixed table converting the handful of catch rates that land on glitch/key-item slots into a real item instead, and Yellow substituting a different byte for PIKACHU/KADABRA/DRAGONAIR/DRAGONITE. Withdrawn on FireRed, it goes into `mon.heldItem` instead: the byte resolves through a fixed table to the Gen 3 counterpart of that Gen 2 item; when there's no byte (a Pokémon deposited on Gen 2) or its item doesn't exist in Gen 3, the species' own wild held item is used (FireRed's `itemCommon`, else `itemRare`), and nothing when it has neither.

## Items

- `depositItem(id, qty, game)` -- `game` is optional but strongly recommended: without it, only the `HM_`/`TM_` id prefixes and anything added through `blacklistItem` are checked -- no `game.data.items` lookup means the key-item flag can't be (Gen 1's `def.keyItem` or Gen 2's `def.pocket == "KEY_ITEM"`). Returns `true`, or `false, "blacklisted"/"is_tm"/"bad request"`. A `TM_`-prefixed id is refused with `"is_tm"` rather than blacklisted while the MOVES tab is on -- deposit it through `depositMove` (below) instead; this only gates new deposits, a TM already in the Bank as an item from before this rule is untouched. With the MOVES tab off (the player's own **MOVES MENU** option or `setMovesTabEnabled(false)`), a TM deposits as a plain item instead, since there's nowhere else for it to go right now.
- `withdrawItem(id, qty)` -- decrements the Bank's own count only. Does **not** touch any bag -- add it to whatever inventory you mean with your own `Bag.add` first (check its return value before calling this, so a failed add doesn't still remove the item from the Bank -- mirrors what this mod's own UI does).
- `tossItem(id, qty)` -- same effect as `withdrawItem` (decrements the Bank's own count), for when the item is meant to just disappear rather than land in a bag -- fires `item_tossed` instead of `item_withdrawn` so a listener can tell the two apart. Returns `true`, or `false, "not enough"`.
- `itemCount(id)`
- `listItems()` -- a plain `{ id = count }` table (a copy; mutating it does nothing to the Bank).
- `isValidItem(id, game)` -- `true` when `id` is a non-empty string present in `game.data.items`. Exported for other mods.
- `validateItemsStorage(game)` -- scans `items` and `orphaned.items` bidirectionally: unknown ids *and* blacklisted ones (`isBlacklisted`, i.e. an HM/key item) move to `orphaned.items`; ids in `orphaned.items` merge back into `items` only if they're both known and not blacklisted -- a quarantined HM/key item stays quarantined even after it becomes otherwise valid. Returns `{ changed, quarantined, restored, lostItems, restoredItems }` (counts are total item quantities, not distinct ids).
- `listInvalidItems()` -- a plain `{ id = count }` copy of the quarantined stacks.
- `invalidItemCount(id)` -- total quarantined quantity for one id, or across every id when `id` is omitted.
- `isBlacklisted(id, game)` -- true for HMs, key items (needs `game` to check Gen 1's `keyItem` flag, Gen 2's `pocket == "KEY_ITEM"` or Gen 3's `KEY_ITEMS` pocket / `importance`), and anything added through `blacklistItem`.
- `blacklistItem(id)` -- adds `id` to the Bank's deposit blacklist, on top of the built-in HM/key-item rule. Additive only -- there is no way to lift the built-in rule for either. Lives only in memory: a mod that needs an id blacklisted calls this itself, every load (matches how `mod.options`/manifest declarations already work -- nothing here is a one-time registration that outlives the calling mod being loaded).
- `setTmItemDepositAllowed(value)` -- forces `depositItem`'s own TM-vs-MOVES-tab rule one way or the other, overriding whatever the MOVES tab's own state would otherwise decide: `true` always lets a TM deposit as a plain item, `false` always refuses it, `nil` clears the override and hands the decision back to the MOVES tab (the default). Lives only in memory, same as `blacklistItem`. Returns `true`.
- `isTmItemDepositAllowed()` -- the read side: whether a TM would deposit as a plain item right now, combining the override above (if any) with the MOVES tab's own state.
- `getTmItemDepositOverride()` -- the raw override itself (`true`/`false`/`nil`), not `isTmItemDepositAllowed`'s computed effective value. For a caller that wants to force it one way and then put back exactly what was there before -- `nil` included, which a captured effective boolean can't tell apart from an explicit `false` -- rather than just turning it back off (LINK's own `depositItemSafe` does this around every deposit, so a TM already sitting as a plain item on either side of a transfer never gets quarantined over this side's own MOVES tab).

## Moves
- `depositMove(id, qty)` -- adds `qty` banked uses of move `id`. Does **not** validate `id` against any game data, and does **not** touch any bag -- remove the matching TM stack from wherever you mean yourself first (mirrors what MANAGE MOVES' own **BAG** page's **DEPOSIT** does, which only ever offers a move that's real). Returns `true`, or `false, "bad request"` for a bad `id`/`qty <= 0`.
- `withdrawMove(id, qty)` -- decrements the Bank's own count only. Does **not** touch any bag -- add `qty` of `tmItemForMove(id)` to whatever inventory you mean with your own `Bag.add` first (check its return value before calling this, so a failed add doesn't still remove the use from the Bank -- mirrors `withdrawItem`). Doesn't itself check `isValidMachine` -- MANAGE MOVES' own **BANK** page lists every banked move but refuses a **WITHDRAW** that fails it before ever calling this (below), and a mod calling `withdrawMove` directly is expected to check it too.
- `tossMove(id, qty)` -- same effect as `withdrawMove` (decrements the Bank's own count), for when the move is meant to just disappear rather than land in a bag as a TM -- fires `move_tossed` instead of `move_withdrawn` so a listener can tell the two apart. Returns `true`, or `false, "not enough"`.
- `moveCount(id)`
- `listMoves()` -- a plain `{ id = count }` table (a copy; mutating it does nothing to the Bank).
- `isValidMachine(id, game)` -- `true` when `id` is a known move in `game.data.moves` **and** some item in the active game still teaches it through machine data (`machine.move`/`teaches`, whatever id that item actually has -- not necessarily `"TM_" .. id`). This is narrower than what keeps a move banked at all (see `validateMovesStorage`): this mod's own **WITHDRAW MOVE** row lists every banked move but checks this before opening the quantity prompt, refusing with a message on a `false` instead. Exported for other mods that want the same "can become a TM right now" rule.
- `validateMovesStorage(game)` -- scans `moves` and `orphaned.moves` bidirectionally, but by a narrower rule than `isValidMachine`: only a move id the active game doesn't recognize **at all** (`game.data.moves[id]` missing -- an uninstalled mod, a different version) is quarantined to `orphaned.moves`; one still recognized moves back if it had been. A move that's still real but currently has no TM stays banked and listed either way -- WITHDRAW MOVE just refuses picking it (see `isValidMachine` above). Also fills any empty move slot on any mon in the Bank, the party or a PC box straight from `orphaned.monMoves` (see `validatePokemonStorage` above) for whatever it's newly valid again, the same thing this mod's own **RELEARN MOVE** row does by hand -- never touching a full moveset, which is why RELEARN MOVE still exists for those. Returns `{ changed, quarantined, restored, lostItems, restoredItems, monMovesRestored }` (counts are total banked uses, not distinct ids, except `monMovesRestored` which counts individual moves filled in this way; `lostItems`/`restoredItems` use the same `{ id, count }` shape `validateItemsStorage` does, since a banked move and a banked item both ultimately came from the same TM).
- `listInvalidMoves()` -- a plain `{ id = count }` copy of the quarantined uses.
- `invalidMoveCount(id)` -- total quarantined uses for one move id, or across every id when `id` is omitted.
- `tmItemForMove(id)` -- the TM item id a move converts to/from, resolved from the active game's item machine data (falls back to `"TM_" .. id` only when no item currently teaches it). Does not check that item actually exists in the active game -- pair with `isValidMachine` first if that matters.
- `canLearn(game, mon, moveId)` -- `true` when `mon`'s own species, or any species it evolved from, could ever learn `moveId` (level-up, TM/HM, or, on Gen 2, an egg move) -- at any level, not a specific one. `false` for an Egg. On Gen 3 it asks the engine's own tables instead (level-up learnset, TM/HM machines and prevolutions, by move number). The same rule TEACH MOVE's own picker filters by, and `isLegal` (above) reuses for its own move check.
- `speciesKnowsMove(def, moveId)` -- the single-species half of `canLearn` above: `true` when `def` (a `game.data.pokemon[species]` record) itself knows `moveId`, with no prevolution walk.
- `prevolutionOf(game, species)` -- the species one level-up/evolution away from evolving into `species`, or `nil` for one nothing evolves into. Cached per active game.

## Money

Same asymmetry as `depositItem`/`withdrawItem`: these only change the Bank's own balance. Neither touches the save's own wallet (`game.save.money` on Gen1, `game.save.player.money` on Gen2) -- debit/credit whatever wallet you mean yourself (mirrors what this mod's own DEPOSIT MONEY/WITHDRAW MONEY do, which already branch on `GameVersion.generation()` to hit the right field).

- `bankMoney()` -- the Bank's own money balance, independent of any save's wallet.
- `depositMoney(amount)` -- adds `amount` to the Bank's balance. Returns `true`, or `false, "bad request"` for an `amount <= 0`.
- `withdrawMoney(amount)` -- subtracts `amount` from the Bank's balance. Returns `true`, or `false, "not enough"` for an `amount <= 0` or greater than `bankMoney()`.
- `maxMoney` -- `999999`, the game's own money cap. Not enforced by `depositMoney`/`withdrawMoney` themselves (the Bank's own balance is a plain number, uncapped) -- only relevant if you're about to add the withdrawn amount to the save's wallet, the same way this mod's own WITHDRAW MONEY caps itself against it first.

## Persistence

Every export above that mutates the Bank only changes the in-memory copy -- the actual write to `storage.lua` (and to every other registered storage's own files, see **Custom storages**) is deferred to line up with the game's own save (a `save.write` hook), not flushed immediately. This is deliberate: see README.md's **Where the data lives** for why an immediate write would let a reset-without-saving duplicate whatever was just deposited. Nothing to do differently here -- just don't assume a mutation is durable the instant the call returns.

On every `save.loaded`, this mod runs `validateStorage(game)` automatically (every entry of every registered storage, see `validate` under **Custom storages**) and, per the player's **REPORT MODE** option, shows the full REPORT screen, a short MESSAGE text box, or nothing at all when anything moved -- plus a separate notice if `recoveredMoney` came back positive. Other mods can call the validation exports directly at any time.

`storage.lua` is **version 7**: `{ version, storageId, entries = { boxes, items, moves, money, timeCapsule }, orphaned = { boxes = { mons, moves }, items, moves, timeCapsule } }` -- the Bank's own data is one registered custom storage (see **Custom storages** below) whose entries are those five keys. Loading a lower version file migrates it and marks the Bank dirty so the upgraded shape is written on the next save. The names used elsewhere in this document (`boxes`, `items`, `orphaned.mons`, `orphaned.monMoves`, `timeCapsule`...) are these entries: `orphaned.mons` lives at `orphaned.boxes.mons` and `orphaned.monMoves` at `orphaned.boxes.moves`. The current Bank box is no longer in the file: it is remembered per save, in that save's own mod data. `entries.boxes` is a dense array of `{ id, name, content }` -- `content` is the array of mons a box used to be directly (before version 6); `name` is replacing the old sparse `boxNames` map. `id` is rolled at random and collision-checked against every one already in use; MANAGE BOX's own **SWITCH** moves a box's `id` along with its `content`/`name` when it swaps two box numbers, since the id identifies that box's contents, not the number they currently sit at. `storageId` is the Bank *itself*'s own id -- one per Bank instance rather than per mon, rolled once the first time anything asks for it and kept from then on (assigned lazily, on first read/validate, rather than through a storage version bump). A PC box's own name is a separate overlay, kept in this save's own `modData` instead (key `pc_box_names`, same sparse shape as the old `boxNames`) rather than in the Bank -- the PC itself lives inside the save, not the Bank, so each save/player keeps its own set instead of sharing one globally.

- `validateStorage(game)` -- the combined pass this mod runs on load: calls every registered entry's `validate(value, orphaned, game)` -- the Bank's own run `validatePokemonStorage`, `validateTimeCapsuleStorage`, `validateItemsStorage` and `validateMovesStorage` -- and marks each storage dirty when one of its entries reports `changed`. Returns `{ changed, pokemon, timeCapsule, items, moves, recoveredMoney, report }` -- `pokemon`/`timeCapsule`/`items`/`moves` are exactly what those four calls themselves returned; `recoveredMoney` is a stray Gen 2 `save.money` this pass found and moved into the Bank, if any (see **Money** above); `report` is `{ lostMons, lostItems, restoredMons, restoredItems }`, merging every lost/restored Pokémon, item and banked move of every storage (see `validate` under **Custom storages**) into the one combined list this mod's own REPORT MODE reads; `storages` is every storage's own results, `{ [id] = { [key] = what its validate returned after changed } }`; `changed` is whether any storage changed. Returns `nil` without a `game`.
- `flush()` -- forces the pending write immediately instead of waiting for the next save, for the Bank and for every registered custom storage. Returns whether anything was actually pending. Normally unnecessary; reach for it only when a mod has its own reason a Bank change must be durable before the game's own save point (e.g. right before code that risks the process, like a native file-picker call).
- `markDirty()` -- marks the Bank's own storage as changed so the next save writes it. Only needed after editing a stored Pokémon in place (the object `getPokemon` returns) without going through another export, which would otherwise not be written until something else touched the Bank.
- `getStorageId()` -- this Bank's own persistent id (a number), assigning one on first call if it doesn't have one yet (marking the Bank dirty when it does). Not a security measure -- a copied `storage.lua` carries this id right along with everything else in it, and it's checked as plain data over LINK the same way `storageVersion` is -- just something LINK (below) can compare to tell two genuinely different Banks apart from a save copied onto another account.

## Cross-generation ids

The same species, item or move is spelled differently in some generations. Each translation is a group `{ Gen 1, Gen 2, Gen 3 }`; an id that isn't in any group (the overwhelming majority) comes back unchanged, so these are safe to call on every id. When the target generation has no slot for it (the thing doesn't exist there) the id also comes back unchanged, and the game treats it as unknown. `targetGen` defaults to `GameVersion.generation()`, i.e. the id spelled the way the game currently running wants it.

- `translateSpeciesId(id, targetGen)` -- `MR_MIME`/`MR__MIME` and `FARFETCHD`/`FARFETCH_D` (Gen 3 spells them like Gen 1).
- `translateItemId(id, targetGen)` -- `THUNDER_STONE`/`THUNDERSTONE`, `ELIXER`/`ELIXIR`, `MAX_ELIXER`/`MAX_ELIXIR`, CRYSTAL_251's old berry names (`PSNCUREBERRY` ... `MIRACLEBERRY`) and `BLACKBELT_I` to Gen 3's (`PECHA_BERRY` ... `LUM_BERRY`, `BLACK_BELT`), and every TM. **A TM is matched by the move it teaches, never by its number** (TM01 is a different move in each generation): `TM_ICE_BEAM` (Gen 1/2 spell it after the move) is Gen 3's item number `301`, whose move is the same. A Gen 3 TM is always its ROM item number (`289`-`338`). Key items and HMs have no entries (the Bank never holds them), and a TM that is an HM in another generation (Rock Smash) has a `nil` there so it is never converted into one. Kanto-Reforged's `TM_G3_<MOVE>` ids are covered too, in the one generation where its host game has no native TM for that move.
- `translateMoveId(id, targetGen)` -- `PSYCHIC_M`/`PSYCHIC`, `CONVERSION2`/`CONVERSION_2` and Kanto-Reforged's `DRAGON_BREATH` to `DRAGONBREATH` (Gen 1 has no such move of its own, so it keeps it).

The Gen 3 ids come from FireRed's own tables; Ruby, Sapphire and Emerald need this cross-check repeated once the game supports them.

## Statistics

Every deposit, withdrawal, removal, teach and LINK exchange is tallied two ways: an all-time total shared by every save that ever used this Bank (`stats.lua`, next to `storage.lua`), and a per-save total scoped to just the active playthrough (written into that save's own `modData`, so it travels and rewinds with the save). The Bank's own entries (`boxes`, `timeCapsule`, `items`, `moves`, `money`, `coins`) keep the same basic counters as any other storage's -- see **Basic counters** under **Custom storages** below.

- `getEntryStats(id, key)` -- `{ bank, player }`: copies of one entry's basic counters, all-time and for the active save; `nil` for an unknown storage or entry. Works for the Bank's own entries (`id = "vrm_pokemon_bank"`) and for every other registered storage.
- `getBankStats()` -- the Bank's own all-time totals in this shape: `{ transactions, pokemon = { deposited, withdrawn, released }, items = { depositedOps, depositedQty, withdrawnOps, withdrawnQty, tossedOps, tossedQty }, moves = { depositedOps, depositedQty, withdrawnOps, withdrawnQty, taught }, money = { depositedOps, depositedTotal, withdrawnOps, withdrawnTotal }, link = { completed, cancelled, sent = { pokemon, items, moves, money }, received = { pokemon, items, moves, money } } }`, plus `peakMoney` (the Bank's own highest-ever balance) and `species` (a `{ speciesId = timesDeposited }` table). `transactions` is every action on the Bank's entries plus every completed LINK. A copy, not a live reference. Built from the basic counters; `getEntryStats` has the rest (TIME CAPSULE, COINS, LINK operations).
- `getSaveStats()` -- the active save's own contribution to those same totals, without `peakMoney`/`species` (those only mean something at the shared-Bank level). A copy, not a live reference.
- `statsScreenId` -- the registered screen id (`mod.content.screens`) behind the **VIEW STATS** row on the OPTIONS > POKéMON BANK page (see README.md), for a mod that wants to push it through its own navigation.

DELETE DATA resets the all-time totals along with everything else in the Bank; a save's own totals aren't part of that, since they live in the save, not the Bank.

## PC menu entry

Pokémon Bank adds a **POKéMON BANK** row to the PC's own main menu (the one offering BILL's PC / Player's PC / PROF.OAK's PC / LOG OFF) through the `ui.pc.items` hook. Two independent ways to control it:

- `setPcEntryEnabled(enabled)` -- pass `false` to hide the row outright regardless of the player's own **SHOW IN PC MENU** option, `true` (or call again) to restore it. Meant for a mod that replaces the PC flow entirely and wants to fold the Bank's entry point into its own UI instead of showing both.
- `pcMenuLabel` -- the exact row label (`"POKéMON BANK"`), for a mod that would rather remove it itself with `mod.ui.removeLabel` inside its own `ui.pc.items` hook (registered with a higher `priority` than this mod's manifest `priority`, so it runs after -- see the engine's decorate-after-`next` hook convention). `setPcEntryEnabled` above is the simpler option for most cases; this is for a mod that wants to make that decision per-call (e.g. only inside its own replacement PC screen) rather than as a standing on/off switch.
- `setPokemonTabEnabled(enabled)` / `setTimeCapsuleTabEnabled(enabled)` / `setItemsTabEnabled(enabled)` / `setMovesTabEnabled(enabled)` / `setMoneyTabEnabled(enabled)` -- same idea as `setPcEntryEnabled`, one level down: hide (`false`) or restore (`true`, or call again) just the POKéMON, TIME CAPSULE, ITEMS, MOVES or MONEY side, independent of the player's own **POKéMON MENU** / **TIME CAPSULE MENU** / **ITEMS MENU** / **MOVES MENU** / **MONEY MENU** options (each combines the same way `setPcEntryEnabled` and **SHOW IN PC MENU** already do -- both the option and the API flag have to allow a tab for it to show). POKéMON and TIME CAPSULE are independent tabs/rows, each with its own toggle -- turning one off doesn't affect the other. With only one tab enabled (by either mechanism), the **POKéMON BANK** row -- and `openBankMenu` below, which is the same chooser -- skips the chooser and opens that tab directly; with none enabled, the row doesn't appear at all and `openBankMenu` returns `false`. Doesn't affect `open(game, tab)`, `openPokemonMenu`/`openTimeCapsuleMenu`/`openItemsMenu`/`openMovesMenu`/`openMoneyMenu`, `pokemonScreenId`, `timeCapsuleScreenId`, `itemsScreenId`, `movesScreenId` or `moneyScreenId` below -- those stay reachable regardless, the same way `open` already bypasses **SHOW IN PC MENU**/`setPcEntryEnabled`.
- `isPcEntryEnabled()` / `isPokemonTabEnabled()` / `isTimeCapsuleTabEnabled()` / `isItemsTabEnabled()` / `isMovesTabEnabled()` / `isMoneyTabEnabled()` -- the read side of the setters above. The player's own **SHOW IN PC MENU** / **POKéMON MENU** / **TIME CAPSULE MENU** / **ITEMS MENU** / **MOVES MENU** / **MONEY MENU** options live inside this mod's `mod.options`, which `mod.find()` does not expose (it only hands back `{ id, version, exports }`) -- these are the only way for another mod to know whether a side is actually visible right now. Each returns the already-combined result (the player's option **and** whatever any mod's setter above last chose), the same value the **POKéMON BANK** PC row itself decides with.

## OPTIONS panel

Pokémon Bank's own **OPTIONS > POKéMON BANK** page can host another mod's own options too. Meant for a companion mod that would rather sit inside this page than add a whole separate one.

- `registerOptionsPanel(panel)` -- `panel` is `{ id, label, description, schema }`: `id` (string, required) is the OWNING mod's own id -- reads and writes go straight into `game.mods.modOptions[id]`/`save.options.modOptions[id]`, so a value set this way is indistinguishable from one the owning mod set through its own `mod.options` (`mod.options_changed` fires with `mod = id`, so the owning mod's own listener for its own options still fires normally). `label` (string, required) is the row shown on this page. `description` (string, optional) is that row's footer text. `schema` (required) is an extended `mod.options:define`. All four documented row types render: `toggle`, `choice` (a popup chooser for more than two choices, direct cycling for two or fewer), `number` (opens `src.ui.QuantityBox`, respecting `min`/`max`) and `text` (opens `src.ui.NamingScreen`, respecting `maxLen`). Any other type in the array is silently skipped. The row's own preview value (`right`) is truncated to a few characters to fit the list -- a `number`/`text` row still stores and edits the full value; only the at-a-glance preview is short. Calling again with an `id` already registered replaces that panel in place (label/description/schema included) rather than adding a second row. Returns `true`, or `false, reason` for a malformed `panel` (a missing `id`/`label`/`schema`, mainly a caller-side bug check, not something to branch on at runtime).
- `unregisterOptionsPanel(id)` -- removes a panel's row; the rows already written to `game.mods.modOptions[id]`/the save are untouched (unregistering only removes the entry point on this page, not the values themselves). Returns whether a panel with that `id` was actually registered.

## PC menu action

The **POKéMON BANK** PC menu itself can host another mod's own row too.

- `registerBankMenuAction(action)` -- `action` is `{ id, label, onSelect, description }`, the first three required: `id` (string) identifies the row for a later `unregisterBankMenuAction`; `label` (string) is what's shown; `onSelect` (function) is called as `onSelect(game)` when the row is picked -- open whatever screen the caller wants from there, same as any other menu row's own `onSelect`. `description` (string, optional) shows in the dialogue box on FireRed's own BANK menu while this row is highlighted (same spot the built-in POKéMON/ITEMS/MOVES/MONEY/LINK rows already use); ignored on Gen 1/2, which has no equivalent box on this menu. Rows appear in registration order, after LINK (which itself comes after the automatic rows a registered storage gets for itself, **Custom storages** below) and before **CANCEL**. A registered action also counts toward whether the **POKéMON BANK** PC row itself shows at all (`isPcEntryEnabled` above) and whether `openBankMenu` skips straight to a single remaining choice, the same way the four built-in tabs and a registered storage's own row already do (see `setPokemonTabEnabled`/etc's own note on that). Calling again with an `id` already registered replaces that row in place rather than adding a second one. Registering an `id` that also has a `registerCustomStorage` storage suppresses that storage's automatic row (see below) -- the two are meant to be used one at a time per `id`, not together. Returns `true`, or `false, reason` for a malformed `action`.
- `unregisterBankMenuAction(id)` -- removes a row. Returns whether one with that `id` was actually registered.

## UI

- `openItemsMenu(game)` / `openMovesMenu(game)` / `openMoneyMenu(game)` / `openPokemonMenu(game)` -- pushes that one tab's own screen directly, no PC or top-level POKéMON/TIME CAPSULE/ITEMS/MOVES/MONEY/LINK chooser required, so another mod can offer any single tab from its own menu. POKéMON's own screen is always **MANAGE PKMN** directly -- TIME CAPSULE is its own separate tab/entry now (see `openTimeCapsuleMenu` under **TIME CAPSULE** above), not nested inside POKéMON's own screen. Returns whatever `mod.ui.push` returns, or `nil, "no game"` without one.
- `openBankMenu(game)` -- the main **POKéMON BANK** entry point itself: the same POKéMON/TIME CAPSULE/ITEMS/MOVES/MONEY/LINK chooser the PC's own **POKéMON BANK** row opens (skipping straight to that one tab, same as the row, when only one is enabled by `setPokemonTabEnabled`/etc and the player's own options). Lets another mod offer this mod's whole entry point from its own menu without routing through a PC. Returns `true` once it's opened something, `false` when every tab is off and there was nothing to open (the row itself just wouldn't appear at all in that case), or `nil, "no game"` without a `game`.
- **On FireRed**, every `open*` here (and `openTimeCapsuleMenu`, `openLinkMenu`, `openCustomStorageEntry` and the pickers) runs the screens on the Bank's own bridge onto Game3's layer stack, whatever `game` you pass (Game3's own, the compat facade `src.core.Game`, or one the Bank's screens handed you): the screens always see the compat facade's `save`/`data`, never Game3's raw ones. A game that is already the bridge's is used as it is. `Screen.entryScreen`/`pickerScreen`, `AmountBox.new` and `askQuantity` only *build* a screen, so pushing it on the right stack stays yours.
- `open(game, tab)` -- a thin dispatcher over `openPokemonMenu`/`openItemsMenu`/`openMovesMenu`/`openMoneyMenu` by name; `tab` is `"pokemon"` (default), `"items"`, `"moves"` or `"money"`. Kept for existing callers -- a new one is better off calling the named export directly. Doesn't route to TIME CAPSULE or LINK -- call `openTimeCapsuleMenu`/`openLinkMenu` directly for those.
- `pokemonScreenId`, `timeCapsuleScreenId`, `itemsScreenId`, `movesScreenId`, `moneyScreenId` -- the registered screen ids (`mod.content.screens`) backing those tabs, for a mod that wants to push them through its own navigation instead of `open`/`openXyzMenu`. Pushing `pokemonScreenId` is exactly `openPokemonMenu`, pushing `timeCapsuleScreenId` is exactly `openTimeCapsuleMenu` -- both go through the same registered factory.

## LINK

- `openLinkMenu(game)` -- pushes the LINK connect screen, same as its own PC-menu row. Returns whatever `game.stack:push` returns, or `nil, "no game"` without one. Ignores the player's own **LINK MENU** option and `setLinkTabEnabled` below -- same convention as `openPokemonMenu`/etc, which bypass **SHOW IN PC MENU**/`setPcEntryEnabled` too.
- `linkScreenId` -- **not** a `mod.content.screens` id (unlike `pokemonScreenId`/etc): LINK's screens are pushed straight onto `game.stack`, like **Pickers** below, so there's nothing to push it *through*. Present for identification only (e.g. a `screen.pushed` listener checking what's on top).
- `setLinkTabEnabled(enabled)` / `isLinkTabEnabled()` -- same idea as `setPokemonTabEnabled`/etc: hide (`false`) or restore (`true`) the LINK side independent of the player's own **LINK MENU** option.

LINK also carries every entry of every registered custom storage, with no extra code from their mods -- see **Custom storages** below.

## Pickers

Four standalone browsing screens for a mod that wants the same SELECT-cycles-storages/Left-Right-flips-boxes browsing without reimplementing it. Each pushes a screen and returns a **handle**, `{ refresh, setFooter, close }`, instead of the picked value directly -- picking happens later, through `opts.onChoose`, possibly much later if that callback itself waits on a further screen (a forget-a-move prompt, a confirmation) -- `handle.refresh()` rebuilds the row list and resets the footer to its default hint, `handle.setFooter(msg)` is `list.footer = msg`, `handle.close()` pops the screen. None of the four assume anything about *why* a mon/box/item/move was picked -- no TO BANK/SWITCH/RELEASE/TOSS submenu is offered after a pick, since that is this mod's own business logic, not something a caller wants assumed for them; `opts.onChoose` is the only thing that runs.

On Gen 3 a PC box has fixed slots, so its list shows one row per slot and an empty slot reads `<EMPTY SLOT>`: it can't be picked, `opts.rowRight`/`opts.dynamicFooter` are never called for it, and `index` is the slot number.

Every `hideX` option defaults to `false` (that view shown); hiding every view for a picker returns `nil, "no views enabled"` instead of pushing anything, and hiding all but one still opens normally with SELECT simply doing nothing (nowhere left to cycle to). `game` is required by all four; omitting it returns `nil, "no game"`.

- `openPokemonPicker(game, opts)` -- browse one Pokémon at a time across the Bank, the party and a PC box. `opts.hideBank`/`opts.hideParty`/`opts.hidePc`, `opts.startView` (`"bank"`/`"party"`/`"pc"`), `opts.rowRight(mon, view, boxNum, index)` (return a string for the row's second line, or `nil` for none), `opts.onChoose(mon, { view, box, index })` (`box` is `nil` on the `"party"` view), `opts.onCancel()`, `opts.title(view, boxNum)`, `opts.footer(view, nextViewLabelOrNil)`. Each row has room for only one second line: setting `opts.rowRight` replaces the level that would otherwise show there.
- `openMovePicker(game, opts)` -- identical to `openPokemonPicker`, except the second line is always **ABLE**/**---** from a required `opts.compatible(mon)` instead of `opts.rowRight` (which this one doesn't take) -- the same annotation TEACH MOVE/RELEARN MOVE show, for a mod with its own idea of what a Pokémon needs to be "compatible" for. Returns `nil, "opts.compatible required"` without one. `---` rather than vanilla PartyMenu's own `NOT ABLE`: this picker is one row per Pokémon, not PartyMenu's two-row entry, and `NOT ABLE` didn't fit the line.
- `openItemPicker(game, opts)` -- browse one item stack at a time across the Bank, the Bag and the player's PC items. `opts.hideBank`/`opts.hideBag`/`opts.hidePc`, `opts.startView` (`"bank"`/`"bag"`/`"pc"`), `opts.rowRight(id, count, view)` (default `"x"..count`), `opts.onChoose(id, count, view)`, `opts.onCancel()`, `opts.title(view)`, `opts.footer(view, nextViewLabelOrNil)`. The Bag view lists in real Bag order (the same order MOVE ITEM's own MOVE reorders); Bank and PC both list alphabetically.
- `openBoxPicker(game, opts)` -- browse a *whole* box at a time across the Bank and a PC box (no Bag/party equivalent -- boxes only exist on those two sides); A confirms whichever box is currently on screen rather than picking a row within it. `opts.hideBank`/`opts.hidePc`, `opts.startView` (`"bank"`/`"pc"`), `opts.requireNonEmpty` (bool, default `true` -- an empty box shows `opts.emptyMessage` instead of calling `onChoose`), `opts.onChoose(view, boxNum)`, `opts.onCancel()`, `opts.title(view, boxNum)`, `opts.footer(view, boxNum, nextViewLabelOrNil)`. A caller that wants a source-then-destination flow of its own (mirroring this mod's own TRANSFER BOX) just calls this twice.

## Custom storages

A mod can register its own storage next to the Bank's: its own data with its own files, statistics, screen, LINK support and quarantine (LOST), without touching anything in this mod. The Bank's own boxes/items/moves/money/time capsule are registered the same way, under `id = "vrm_pokemon_bank"`, so there is one system, not two.

```lua
local bank = mod.find("vrm_pokemon_bank")
if bank and bank.exports.registerCustomStorage then
  local MultiMap = bank.exports.MultiMap
  local ok, err = bank.exports.registerCustomStorage({
    id = mod.id,                       -- your own mod id (see the rules below)
    name = "My Storage",
    storageVersion = 1,
    entries = {
      {
        key = "coins", label = "COINS", storageFormat = "single",
        freshStorage = function() return 0 end,
        normalizeStorage = function(v) local n = math.max(0, math.floor(tonumber(v) or 0)); return n, n ~= v end,
        link = { prefix = "C" },
      },
      {
        key = "berries", label = "BERRIES", storageFormat = "multi-map",
        freshStorage = MultiMap.fresh,
        normalizeStorage = MultiMap.normalize,
        validate = MultiMap.validate,
        link = { nameOf = function(game, id) return id end },
      },
    },
  })
  if not ok then mod.log:warn("could not register: %s", tostring(err)) end
end
```

### Registration

- `registerCustomStorage(config)` -- returns `true`, or `false, reason` (a missing or malformed field, an unknown or repeated `id`, a repeated entry `key`, an invalid entry). `config` is `{ id, name, storageVersion, statsVersion, migrate, entries, description, menu }`. `description` (string, optional) shows in the dialogue box on FireRed's own BANK menu while this storage's automatic row (below) is highlighted, same as `registerBankMenuAction`'s own `description` above; ignored on Gen 1/2.
  - `id` (string, required) is the id of the registering mod. It is a plain self-declared string, **not** trusted: it must resolve through `mod.find` (a real, active mod) and must not already be registered -- the first registrant keeps it for good. Nothing else identifies the caller, so these two rules are the whole protection against one mod taking another's storage.
  - `name` (string, required) is shown in the UI. `entries` (array, required, at least one) is described below.
  - `storageVersion` / `statsVersion` (numbers, default `1`) version the storage file and the statistics file. LINK compares `storageVersion` (see below).
  - `migrate(decoded)` (function, optional) runs on the whole decoded storage file (`{ version, entries, orphaned }`) before the per-entry normalization; return a truthy value when it changed something. The Bank uses it for its own version migrations.
  - `menu` (optional): `"storage"` (default) gives the storage one BANK menu row; `"entries"` gives each entry a row of its own (below), the way the Bank's own POKéMON/ITEMS/... are.
- A successful registration also adds a **`<NAME> MENU`** toggle (`show_<id>_tab`, on by default) to the Bank's own OPTIONS page -- with `menu = "entries"`, one **`<LABEL> MENU`** toggle per entry instead (`show_<id>_<key>_tab`). `isCustomStorageTabEnabled(id, key)` reads it (`key` optional: an entry's own toggle, else the storage's; `true` when there is none). `setCustomStorageTabEnabled(id, enabled, key)` is the same idea as `setPokemonTabEnabled`/etc above: an override independent of the player's own option, combined with it the same way (both have to allow the row for it to show); `false, "unknown custom storage"` when there's no such toggle. The Bank's own entries answer here too, under their own options (`isCustomStorageTabEnabled("vrm_pokemon_bank", "items")` is `isItemsTabEnabled()`'s toggle).
- **The BANK menu gets rows for your storage automatically**, in registration order after the Bank's own (which are its entries' rows) and **before LINK**: one per registered `id`, labeled with `name` and, on FireRed, showing `description` (above) in the dialogue box while highlighted, shown whenever the toggle above allows it and at least one unlocked entry has a `screen` (below); one entry with a screen opens it directly, more than one opens a chooser of their `label`s first. With `menu = "entries"`, one row per unlocked entry with a screen instead, labeled with its `label`, showing its `description`, under its own toggle, opening its `menuScreen` (or its `screen` without one). Nothing to register, nothing to react to `mod.options_changed` for; `registerBankMenuAction` rows (below) come after LINK instead. The one exception: an `id` that already has a row from `registerBankMenuAction` (above) keeps only that hand-registered row -- a mod that wants its own label or its own gating registers one there instead (the PokéWalker mod doesn't: it takes the automatic row and checks whether the Pokéwalker mod itself is active inside its `screen`), and the automatic row for that `id` is skipped so there is never a duplicate.
- There is **no `unregisterCustomStorage`**, on purpose. A registered id is permanent for the session: if it could be released, another mod could call `registerCustomStorage` right afterwards and take it -- and with it the files, statistics and LINK slot of the previous owner -- and nothing would let the Bank tell the real owner from an impersonator. `vrm_pokemon_bank` itself cannot be impersonated: it registers itself synchronously while loading, before `registerCustomStorage` is exported to anyone.
- **File names** are always `bank/<id>_storage.lua` and `bank/<id>_stats.lua` (each with its own `.bak`/`.tmp`). The one exception, `bank/storage.lua` and `bank/stats.lua` without a prefix, is the Bank's own storage and is not available to anyone else.
- Every function you provide is called inside a `pcall`: an error is logged and treated as "nothing returned" (a `normalizeStorage` that errors leaves the value as it was; a `validate` that errors changes nothing; a `deposit`/`withdraw`/`link.isValid` that errors refuses).

### Entries

Each entry is one independent piece of data inside the storage (`entries[key]` in the file, `orphaned[key]` for what is set aside):

| Field | |
|---|---|
| `key`, `label` | required. `key` is unique within the storage; `label` is shown in the UI (LINK rows, VIEW STATS pages). |
| `shortLabel` | optional string, for tight spots: LOST prefixes and LINK's SEND summary (default: `label`). On Gen 1/2 that summary drops a label that doesn't fit whole next to its value. |
| `storageFormat` | required: `"single"`, `"array"`, `"map"`, `"multi-array"` or `"multi-map"` (below). Any other value is rejected. |
| `freshStorage()` | required. The entry's default value. |
| `normalizeStorage(value)` | required. Returns `value, changed`: repair or migrate the loaded value (mutate it and/or return a new one). Runs on every load. |
| `validate(value, orphaned, game)` | required unless `"single"`. Moves what the game no longer recognizes from `value` into `orphaned` and what became valid again back; mutates both, returns whether it changed anything and, optionally, a second value that `validateStorage` hands back; when that value has the load report's own lists -- `lostMons` (`{ species, from }`), `lostItems`/`restoredItems` (`{ id, count, from }`, or `{ element, from }` for a list element, named the way LINK and LOST name it), `restoredMons` -- they join the report shown when a save loads (`MultiMap.reconcile`/`MultiArray.reconcile` already return them). `from` defaults to the entry's `label`. Runs when the file loads (no `game`: check only the shape) and again, with the `game` just loaded, every time a save loads (`validateStorage`) -- the one to check ids against `game.data`. `orphaned` is the entry's own bucket (`{}` at first) and is never passed for `"single"`. |
| `orphanList(bucket)` | optional, `array`/`multi-array`: when `orphaned[key]` keeps more than the list of set-aside elements, returns that list -- the one LOST shows and LINK carries (default: the bucket itself). The Bank's own `boxes` keeps `{ mons, moves }` there and returns `mons`. |
| `freshStats()` / `normalizeStats(value)` | statistics counterpart of the two above. `normalizeStats` is required; `freshStats` defaults to `{}` and is required when `stats` is given. This table is only the entry's own extra statistics: the basic counters are kept by the Bank (see **Basic counters**). |
| `description` | optional text, shown on FireRed while the entry's BANK menu row is highlighted (`menu = "entries"`). |
| `menuScreen` | optional, `menu = "entries"`: what the entry's BANK menu row opens (same forms as `screen`), when it isn't `screen` itself. |
| `withdraw`, `deposit` | optional transfer rules used by LINK (below). |
| `stats` | optional. Extra rows for the entry's page in VIEW STATS: a list of `{ label, value(game, statsValue), description }` (below). |
| `link`, `linkEnabled` | optional. `link` customizes LINK (below); `linkEnabled = false` keeps the entry out of LINK (default `true`). |
| `screen` | optional. The entry's own screen: a function, or an array of containers (see **Screens**). |
| `isUnlocked(game)` | optional. Whether the entry is reachable in the current game state (e.g. only after getting a key item). A locked entry is left out of the BANK menu, and its row in LINK's SEND menu says it isn't unlocked yet instead of opening (RECEIVE still shows what arrives for it); with no function it is always unlocked, and one that errors counts as locked. Every `*.entry(config)` builder passes `config.isUnlocked` through. |

### Formats

The Bank does not interpret the data: everything format-specific lives in your callbacks. The format tells LINK and LOST the *shape* to expect, and `validate`/orphaned data are skipped for `"single"`.

| Format | Value in `entries[key]` | Bucket in `orphaned[key]` | LINK / LOST unit |
|---|---|---|---|
| `single` | one number | none | an amount |
| `map` | flat `{ [id] = qty }` | `{ [id] = qty }` | an id with a quantity |
| `array` | list of elements (any table) | list of elements | one element |
| `multi-array` | list of containers `{ id, name, content = { element... } }` | list of elements | one element, per container |
| `multi-map` | list of containers `{ id, name, content = { [id] = qty } }` | `{ [containerId] = { [id] = qty } }` | an id with a quantity, per container |

`mod.exports.MultiMap` has ready-made helpers for `multi-map` (the container shape is the same as the Bank's own boxes: `id` is rolled and unique, `name` is optional):

- `MultiMap.fresh()` / `MultiMap.normalize(value)` / `MultiMap.validate(value, orphaned)` -- drop them straight in as `freshStorage`/`normalizeStorage`/`validate`. `normalize` keeps unique container ids, drops non-positive or non-integer quantities and always leaves at least one container; `validate` is structural hygiene on the orphaned buckets only.
- `MultiMap.newContainer(containers, name)`, `MultiMap.container(containers, id)` (returns `container, index`), `MultiMap.add(container, id, qty)`, `MultiMap.remove(container, id, qty)` (both return whether they did something), `MultiMap.total(containers, id)`.
- `MultiMap.reconcile(containers, orphaned, isValid)` -- for your own `validate`: ids `isValid` rejects move into `orphaned[containerId]`, and orphaned ids that became valid go back to their container (or the first one if it is gone). Returns `{ quarantined, restored, lostItems, restoredItems }`.

`mod.exports.MultiArray` is the same idea for `multi-array` (element shape is yours -- there's no id to key an entry by, so `orphaned[key]` is a flat list instead of one bucket per container):

- `MultiArray.fresh()` / `MultiArray.normalize(value)` / `MultiArray.validate(value, orphaned)` -- drop them straight in as `freshStorage`/`normalizeStorage`/`validate`. `normalize` keeps unique container ids and always leaves at least one container; `validate` never touches the flat orphaned list (there's nothing structural to check on an arbitrary element).
- `MultiArray.newContainer(containers, name)`, `MultiArray.container(containers, id)` (returns `container, index`), `MultiArray.insert(container, element)`, `MultiArray.removeAt(container, index)` (returns the removed element), `MultiArray.total(containers)`.
- `MultiArray.reconcile(containers, orphaned, isValid)` -- for your own `validate`: elements `isValid` rejects move into the flat `orphaned` list; ones that became valid again go back into the *first* container (there's no original one to remember). Returns `{ quarantined, restored, lostItems, restoredItems }`.

`MultiArray.entry(config)`/`MultiMap.entry(config)` go one step further: they build the **whole entry** -- `storageFormat`, `freshStorage`, `normalizeStorage`, `validate` and `screen` all resolved -- ready to drop straight into `registerCustomStorage`'s `entries`:

```lua
local MultiArray = bank.exports.MultiArray
entries = {
  MultiArray.entry({
    key = "queue", label = "QUEUE",
    getContainers = function(game) return bank.exports.getCustomStorageEntry(mod.id, "queue") end,
    getCurrent = function(game) return myCurrentQueueId end,
    renderRow = function(game, element, index) return { label = element.name, value = index } end,
  }),
}
```

- `config.key`/`config.label` (required, same as any entry), `config.description`, `config.freshStats`/`normalizeStats`/`stats`/`linkEnabled`/`link` (all optional, passed straight through to the built entry as `entry.freshStats`/`normalizeStats`/`stats`/`linkEnabled`/`link`, same contracts as always -- `entry.link` is LINK's own `nameOf`/`labelOf`/`isValid`/`prefix`/`commit` table, see **`entry.link`** below). `config.linkWithdraw`/`config.linkDeposit` (optional) become `entry.withdraw`/`entry.deposit`, LINK's own `(game, poolId, ref, qty/value)` hooks (see **`entry.withdraw` / `entry.deposit`** above) -- named apart from `config.withdraw`/`config.deposit` below on purpose, since those are a different contract (the subscreen container's own TRANSFER, `(game, pageId, row, destContainerId, env)`); reusing one function for both would call it with the wrong arguments from whichever side didn't ask for it. Neither is required: LINK already moves `multi-array`/`multi-map` data generically by `poolId` without any hook.
- `config.getContainers(game)` (required) -- reads this entry's own live containers array (typically a thin wrapper around your own `getCustomStorageEntry(id, key)`, same as any entry closes over its own storage internally).
- `config.fresh`/`config.normalize`/`config.validate` (optional) -- override the format's own `fresh`/structural `normalize`/`validate` (above) entirely; omit them to use those as-is. `config.fresh` is for an entry that always starts with a fixed, non-arbitrary set of containers (known ids, not one auto-generated one) -- e.g. two containers your mod always creates, never lets the player add or remove.
- `config.screen`/`config.subscreen` (both optional, function or array -- same duality as the general `screen` contract): `subscreen` manages the content of **one** container -- its array form is a single container whose **pages are the containers themselves** (`getPages`, the exact same mechanism `Pokemon.lua`'s own `bankContainer` already uses for boxes), so `build(game, pageId, env)` gets the container's id as `pageId` directly, no extra digging needed; `screen` is the thin navigation shell around it (below). Omit `subscreen` for a usable-but-plain default (`id`/quantity rows for `MultiMap`; `tostring(element)` for `MultiArray` unless `config.renderRow(game, element, index, env)` says otherwise). Omit `screen` to get the shell described below; provide it (a `function(game) ... end`) to take full control instead -- and if `subscreen` is also a function, it gets the *current* container directly as its 2nd argument (no `pageId` to read there, since it isn't a `getPages` container at all).
- `config.getCurrent(game, env)` (optional) -- which page is "current" (a container id, or a position with `pageIdBy = "index"`); without it, the default `screen` always opens on the first container. `env` is the open screen's handle (`nil` when the function form of `subscreen` is used). Navigating never persists this on its own (same as the Bank's own BOXES: only an explicit action -- e.g. your own row in `listPagesActions` -- would).
- `config.setCurrent(game, pageId, env)`, `config.autoRememberPage`, `config.rememberPageLabel` (optional) -- the default subscreen's `setRememberedPage`/`autoRememberPage`/`rememberPageLabel` (see **Screens**): with `autoRememberPage = false` navigating never calls `setCurrent`, only **CHANGE** in the pages list does, and the current container gets its mark. The Bank's own BANK boxes work this way.
- `config.pageIdBy` (optional, `"id"` by default) -- `"index"` makes each page's id its container's **position** (1, 2, ...) instead of the container's own `id`, e.g. to line up with a numbering your own API already exposes (the Bank's BANK boxes use this, so a box's page id is its box number). Every callback that gets a `pageId` gets that position.
- `config.pageLabel(game, container, index)` (optional) -- a page's label; defaults to the container's `name`, or `<label> <index>` without one.
- `config.containerId` (optional, `"content"` by default) -- the default subscreen container's own `id` (what TRANSFER destinations, `env.pageOf` and `jumpTo` refer to it by).
- `config.canListPages` (optional, `true` by default) -- `false` drops the automatic **PAGES** row (below), e.g. when your own START row already covers it.

The default `screen` opens directly on the current container's content (`subscreen`, resolved or your own or the plain default). **START** works exactly like any other `canListPages` container (see **Screens** above): with more than one container, it offers a **PAGES** row (`config.listPagesLabel`) that opens the list of every one (with their counts); **VIEW** jumps the same open screen to the one you pick -- `config.listPagesActions` adds rows after **VIEW**, e.g. `RENAME`/`DELETE`, each getting the chosen container's id as `pageId`, and `config.canRearrangePages`/`config.onMovePage` add **MOVE** to reorder them (your `onMovePage` reorders your own containers array). With a single container (e.g. a party-like entry with nothing to switch between) `getPages` itself returns nothing to page through, so **START** behaves exactly as it would without any of this.

`config.renderRow`/`onAction`/`onStart`/`slots`/`canOverflow`/`emptySlots`/`emptySlotLabel`/`canRearrangePages`/`onMovePage`/`listPagesColumns`/`listPagesIcon`/`listPagesOnStart`/`listPagesFooter`/`columns`/`icon`/`dynamicFooter`/`draw`/`canRearrange`/`canRearrangeBetweenPages`/`onMove`/`withdraw`/`deposit`/`canWithdraw`/`canDeposit`/`transferLabel`/`canTransfer`/`heldItemMarks`/`title`/`emptyMessage`/`listOpts` feed the *default* `subscreen` (`renderRow` is `(game, element, index, env)` for `MultiArray` and `(game, id, qty, env)` for `MultiMap`; `canRearrange`/`canRearrangeBetweenPages`/`onMove`/`heldItemMarks` are `MultiArray` only; `listOpts` is copied on every build) (ignored if you provide your own `subscreen`) -- same fields and meaning as any container in the general `screen` contract above, including which container they're showing: it's `pageId`, the same argument any `getPages` container's own callbacks already get, not a special MultiArray/MultiMap thing.

`MultiArray.subscreen(config)`/`MultiMap.subscreen(config)` return that default subscreen on its own (the same one-container array, same `config` fields, `getContainers` required), for a mod that builds its own `screen` around it -- e.g. next to containers of its own. The Bank's own **BANK** container in MANAGE <PK><MN> is exactly this, next to PARTY and PC.

`mod.exports.Map`/`mod.exports.Array`/`mod.exports.Single` are the same idea for `map`/`array`/`single` -- no containers, so no `getContainers`/`getCurrent`/PAGES-as-containers, but `Map`/`Array` still page, by **category computed from the content** instead of by container (the Bank's own `items`/`moves` do exactly this: pockets and move types). The Bank's own storage (`lib/Storage.lua`) is registered entirely through these five `.entry()` builders, as a worked example of what a third-party mod's own registration would look like:

```lua
local Map = bank.exports.Map
entries = {
  Map.entry({
    key = "stash", label = "STASH",
    getStore = function(game) return bank.exports.getCustomStorageEntry(mod.id, "stash") end,
    categoryOf = function(game, id) return myCategoryOfId(id) end,
    categoryOrder = { "BALLS", "MEDICINE" }, -- or a function(game, ids) -- see below
  }),
}
```

- `Map.fresh()`/`Map.normalize(value)`/`Map.validate(value, orphaned)` -- structural only, same shape as the Bank's own `items`/`moves` today: `normalize` just ensures the value is a table (individual quantities are never sanitized -- your own deposit/withdraw is what should never leave a zero-or-negative count behind); `validate` prunes non-positive/non-numeric quantities from the **orphaned** bucket only, the live map is untouched. `Map.add(store, id, qty)`/`Map.remove(store, id, qty)`/`Map.total(store, id)` are the same small conveniences `MultiMap` has, without the container.
- `Array.fresh()`/`Array.normalize(value)`/`Array.validate(value, orphaned)` -- same idea, `array`-shaped (a plain list); `validate` is a structural no-op, same reasoning as `MultiArray.validate` (nothing generic to check on an arbitrary element) and the same rule the Bank's own `timeCapsule` already followed. `Array.insert(store, element)`/`Array.removeAt(store, index)`/`Array.total(store)`.
- `Single.fresh()`/`Single.normalize(value, max)` -- clamps to a non-negative integer, optionally capped by `max`, same as the Bank's own `money`.
- `Map.entry(config)`/`Array.entry(config)` -- `config.key`/`label`/`description`/`normalize`/`validate`/`freshStats`/`normalizeStats`/`stats`/`linkEnabled`/`link`/`linkWithdraw`/`linkDeposit` mean exactly what they do for `MultiArray.entry`/`MultiMap.entry` above. `config.getStore(game)` (required) reads the entry's own live flat value (a map or a list -- not an array of containers, there's only one implicit pool, same as `map`/`array`'s own row in the **Formats** table). `config.screen`/`config.subscreen` are the same function-or-array duality; the default `subscreen` is one container listing the store's contents (`config.renderRow(game, id, qty, env)` for `Map`, default `id`/quantity rows; `config.renderRow(game, element, index, env)` for `Array`, default `tostring(element)`). `Array`'s default also takes `config.canRearrange`/`onMove` (a plain list has a real order to reorder, unlike a map). Both defaults take `config.columns`/`icon` (the grid, above).
- **Category pagination** (opt-in via `config.categoryOf(game, idOrElement)`, both `Map` and `Array`): `getPages` groups the content by category instead of by container. `config.categoryOrder` is either an array (a fixed canonical order, like the Bank's own `ITEM_POCKETS` -- entries are `{ id, label }` or a plain string treated as both, filtered down to whatever categories are actually present) or a function `function(game, idsOrElements)` that returns the finished `{ id, label }` page array itself (e.g. an alphabetical sort over whatever's present, the Bank's own move types); neither given defaults to alphabetical by category id. `config.includeAllPage` (default `true`), `canListPages`/`listPagesLabel`/`listPagesActions` mean the same as the general `screen` contract.
- **`config.globalAllPage`** (default `false`) -- **there are two different real behaviors for the ALL page, matching an actual divergence already in the Bank's own containers, not a hypothetical**: by default (`false`), ALL uses the engine's own `includeAllPage` (`ALL_PAGE_ID`) -- each category's own rows concatenated in `categoryOrder`, sorted only *within* each category, same as the Bank's own `items` pockets. With `globalAllPage = true`, ALL is a page of its own that `build` treats as "no category filter" -- a truly flat, global sort across every category, same as the Bank's own move types (which deliberately avoid `includeAllPage` for exactly this reason: concatenation can't give a global order when a category's own sort position doesn't match its contents').
- `Single.entry(config)` -- same passthrough fields; no `subscreen`/category pagination (nothing to list for one bare number) and no `validate` (the base contract skips it for `single`). `config.max` (optional) caps the default `normalizeStorage`'s clamp. `config.screen` is a plain passthrough, function or array -- in practice always a function, since `single` has no rows to manage (the Bank's own `money` opens its own `AmountBox` UI).

### Reading and writing the data

- `listCustomStorages()` -- every registered storage, as its live record (`id`, `name`, `storageVersion`, `statsVersion`, `entries`, `entryIndex`, `storageFilename`, `statsFilename`, `flush()` and `isDirty()`, among others).
- `getCustomStorage(id)` -- one record, or `nil`.
- `getCustomStorageEntry(id, key)` -- the live value of an entry (mutate it, then persist it with `setCustomStorageEntry`), or `nil` for an unknown id/key.
- `setCustomStorageEntry(id, key, value)` -- replaces an entry's value and marks the file dirty. Returns `true`, or `false, "unknown custom storage"/"unknown entry"`. Anything you mutate in place through `getCustomStorageEntry` is only written after you call this, so call it whenever you change something.
- `getCustomStorageOrphaned(id)` -- the live `orphaned` table of a storage (`orphaned[key]` per entry).
- `getCustomStorageStats(id, key, scope)` / `setCustomStorageStats(id, key, value, scope)` -- the same pair for an entry's own statistics table. It exists twice, with the same shape (`freshStats`/`normalizeStats`): all-time in `bank/<id>_stats.lua` (`scope = "bank"`, the default) and for the active save in its own mod data (`scope = "player"`). The Bank only *stores* them: your mod updates them with whatever it wants to track on top of the basic counters.
- `updateCustomStorageStats(id, key, update)` -- the usual way to count something: calls `update(value, scope)` on both tables, all-time and this save's, so they always move together (mutate `value`, or return a table to replace it). Returns `true`, or `false, reason` (an unknown storage or entry, an `update` that isn't a function or that errors).
- `recordCustomStorageAction(id, key, action, amount)` -- reports a deposit (`action = "deposit"`), withdrawal (`"withdraw"`) removal (`"remove"`: something your screen threw away or released for good) or use (`"use"`: something consumed without leaving the storage, counted only as an action) of `amount` (default `1`) into the entry's basic counters, all-time and for the active save; call it whenever your own screen moves something in or out. `amount` is the units moved on `map`/`multi-map`/`single` (one operation plus `amount` units) and the elements moved on `array`/`multi-array`. It fires `storage_action` (see **Events**), where the statistics come from. Returns `true`, or `false, "unknown action"/"unknown entry"` (the Bank's own entries included, since they have their own events).
- `getEntryStats(id, key)` -- the entry's basic counters (see **Statistics** above).
- `listCustomStorageFiles()` -- `{ id, storageFile, statsFile }` per storage.
- `isCustomStorageEntryUnlocked(id, key, game)` -- `entry.isUnlocked(game)` as a boolean: `true` when the entry has no such function, `false` for an unknown id/key or when it errors.
- Writes are deferred to the game's own save, like the Bank's own (see **Persistence**); `flush()` writes every storage.

**RESTORE DATA / DELETE DATA** (OPTIONS > POKéMON BANK) reach every registered storage, the Bank's own included. RESTORE DATA restores each storage's `<id>_storage.lua.bak` (best effort: one with no valid backup is left as it is) and **never** the `<id>_stats.lua` files. DELETE DATA erases the whole `bank/` folder -- both files of every storage, backups included -- and resets them.

### `entry.withdraw` / `entry.deposit`

Optional. They are your entry's own rules for moving something out of, or into, its data when **LINK** does it; without them LINK edits the entry's data directly (a map or list gets the item removed or added, a `single` gets its number changed).

- `withdraw(game, poolId, ref, qty)` -- takes something out and returns what was taken: the quantity (`map`/`multi-map`), the element (`array`/`multi-array`) or the amount (`single`). Return `nil`/`false` to **refuse**: nothing is removed and nothing goes into the send cart. The hook itself removes it from your data.
- `deposit(game, poolId, ref, value)` -- stores something and returns anything but `false` to accept; `false` **refuses**. The hook itself stores it.
- `poolId` is the container id on `multi-array`/`multi-map` and `nil` otherwise; `ref` is the map id or the list index (`nil` for `single`); `value` is the quantity, the element or the amount.
- What a refusal means: a refused withdraw simply leaves the thing in the storage. Something a refused deposit cannot place -- taking back a cancelled offer, or receiving -- is not lost: a `map`/`array`/`multi-*` item goes to LOST (`orphaned[key]`, in the container it came from when there is one), and a `single` amount is added anyway, since an amount cannot be set aside.

### Basic counters

The Bank keeps these for every entry of every storage (its own included), all-time in the `basic` root of `bank/<id>_stats.lua` and per save in the save's own mod data. Nothing to register: they come from `recordCustomStorageAction` (above) and from LINK, which the Bank records itself.

| Counter | Formats | Counts |
|---|---|---|
| `transactions` | all | Actions on the Bank's side: deposits, withdrawals, removals (never LINK). |
| `links` | all | Completed LINK exchanges in which the entry sent or received anything (one per exchange). |
| `deposited` / `withdrawn` | all | Deposit / withdrawal operations; on `array`/`multi-array`, the elements moved. |
| `sent` / `received` | all | What LINK moved: elements on `array`/`multi-array`, distinct ids on `map`/`multi-map`, one per exchange on `single`. |
| `depositedQty` / `withdrawnQty` / `sentQty` / `receivedQty` | `map`, `multi-map`, `single` | The units (or amount) behind those operations. |
| `removed` / `removedQty` | all / `map`, `multi-map`, `single` | Only created by the first `"remove"`; until then they're absent. |
| `peak` | `single` | The highest balance seen after a deposit or a LINK. |

Older files move over by themselves: the old basic counters (`deposited`/`withdrawn`/`linkSent`/`linkReceived`, amounts on formats that hold them) become the matching units, and an entry with no basic counters yet is seeded from its own statistics table if that still holds the old default (`transactions`/`deposited`/`withdrawn`), or a `peak` on a `single` entry.

### `entry.stats`

Every entry of every storage gets its own page in **VIEW STATS**, the Bank's own first (named after the storage when it has a single entry, after the entry's `label` otherwise), flipped with Left/Right; SELECT switches it between the all-time (**BANK**) and the active save's (**PLAYER**) counters. The page always starts with the basic counters above: **ACTIONS**, **DEPOSITED**, **WITHDRAWN**, **REMOVED** (only once above zero), and when `linkEnabled ~= false`, **LINKS**, **SENT** and **RECEIVED**; formats with units add a **QTY** row after each (**DEP. QTY**, **WDR. QTY**, **REM. QTY**, **SENT QTY**, **RECV QTY**), and `single` ends with **PEAK**. Amounts of a `single` entry show `link.prefix` in front.

`stats` adds rows after them, on both sides (each with that side's own table): a list of rows, shown in order, each `{ label = "HITS", value = function(game, statsValue) return ... end, description = "..." }`. `label` (string) and `value` (function) are required, `description` (string) is optional; registration is refused otherwise. `value` gets the entry's own statistics table for the side shown (`getCustomStorageStats`) and returns what the row shows, and optionally a second string that replaces the row's `label` (the Bank's own **TOP** row names the species this way); `nil` hides the row, and an error drops only that row.

```lua
stats = {
  { label = "HITS", description = "Times it was hit.", value = function(_, s) return tostring(s.hits) end },
},
```

### LINK

LINK carries every entry that has `linkEnabled ~= false`, with no code from you: what it sends and how is derived from `storageFormat`.

- **Negotiation.** Each side's `bank_hello` lists its storages as `{ id, storageVersion, entries }` (LINK-enabled entries only). A mismatch never ends the session: an entry whose storage or key the other player doesn't have, or whose `storageVersion` differs, simply shows its reason instead of opening. What still cancels the whole session is what makes it meaningless: a different LINK version, linking with yourself, or with your own Bank.
- **Send.** Each entry gets a row in the SEND menu (the Bank's own first, in registration order) and a picker: an amount menu for `single`, otherwise a list of the entry's data (one page per container on `multi-array`/`multi-map`) with SEND / TAKE BACK. The cart keeps things per container; on the wire it is flattened, and the receiver puts everything into its **first** container unless `link.commit` says otherwise. Sending and receiving are not deposits or withdrawals: they only count in the LINK counters.
- **Receive.** Every received id/element goes through `link.isValid` (and, for lists, `link.prepare`); accepted data is committed to the entry, rejected data lands in its `orphaned[key]` (LOST). A cancelled or failed session hands everything back through the same rules (see `entry.deposit` above).
- `entry.link` (all fields optional):
  - `nameOf(game, id)` -- display name of a map id (default: the id).
  - `labelOf(game, element)` -- display text of a list element (default: its `nickname`, `name`, `species` or `id`, else `tostring`).
  - `isValid(game, value)` -- `false` sends a received id (`map`/`multi-map`) or element (`array`/`multi-array`) to LOST. Never called for `single`. Absent: everything is valid.
  - `prefix` (string) -- text put before a `single` amount (`"W"` shows `W120`).
  - `commit(value, payload)` -- called with the entry's live value and the accepted data (`{ [id] = qty }` or a list) to store it your own way; return `false` to fall back to the default. Not used for `single`.
  - `prepare(game, element, sender)` -- `array`/`multi-array`: readies each accepted element as it arrives, before anything shows it (e.g. converting it for the game running now); return the element to keep (`nil` keeps the one given). `sender` is `{ storageId }`, the other player's Bank id.
  - `pokemon` (boolean) -- `array`/`multi-array`: the elements are POKéMON. Their lists show each one's level, name it by default, and offer **STATS** (its summary).
  - `footer(game, value, nextLabel)` -- the text under the highlighted row of the pickers: `value` is the map id or the list element, `nextLabel` the container SELECT switches to. Default: only the SELECT hint.
  - `poolLabel(game, container, index)` -- `multi-*`: a container's page name (default: its `name`, else `#index`).
  - `currentPool(game)` -- `multi-*`: the id of the container the picker opens on (default: the first).

### LOST

**VIEW LOST** and the LINK LOST screens list what each storage set aside. Their pages are the registered storages (one page per `CustomStorage.id`, shown only when there is more than one), each listing the orphans of *all* its entries -- also those with `linkEnabled = false` on VIEW LOST -- prefixed with the entry's `shortLabel` (the Bank's own: `BOX`, `CAPS`, `ITEM`, `MOVE`). Moving a row in LINK's LOST does not fire deposit/withdraw events or statistics.

### Screens

`entry.screen` is either a function `function(game) ... end` that opens whatever you want, or an **array of containers**, which the Bank turns into a list screen with the same controls as MANAGE PKMN. `openCustomStorageEntry(game, storageId, key)` opens it (`true`, or `false, "no screen"`; an array is opened with the item counter on).

```lua
local Screen = bank.exports.Screen
game.stack:push(Screen.entryScreen(game, containers, opts))   -- management: MOVE / REMOVE / TRANSFER between containers
game.stack:push(Screen.pickerScreen(game, containers, opts))  -- choosing one row (or one page)
```

`containers` is the array (SELECT cycles between them), `opts` is `{ screenId, readOnly, counter, onClose, startView, data, heldItemMarks }` plus `onChoose` (required for the picker). Both functions return the screen; `screen.refresh(preserveCursor)` rebuilds the current container and `screen.jumpTo(containerId, pageId, preserveCursor)` switches container/page in place.

**Container** (every callback receives `game` first and `env` last):

- `id`, `label` (required) -- `label` is the default title and the text in the generated `TO <label>` rows. `emptyMessage` -- footer when there are no rows. `title(game, pageId, env)` -- overrides the title.
- `getPages(game, env)` -- array of `{ id, label }` when the container has pages (left/right flips them); `nil` when it doesn't. `includeAllPage = true` puts an aggregate **ALL** page first (`Screen.isAllPage(pageId)` recognizes it). `onPageChange(game, pageId, env)`; `getRememberedPage(game, env)` / `setRememberedPage(game, pageId, env)` -- the page you keep yourself: the screen opens on it (without `getRememberedPage` it opens on the first; `screen.jumpTo` opens another one without remembering it). `autoRememberPage` (default `true`) calls `setRememberedPage` whenever the page changes (left/right, **VIEW** in the pages list; never for ALL). Set it to `false` for a page that is a deliberate choice rather than the last one seen -- like the Bank's current box: navigating then never remembers, the pages list (`canListPages`) gets a **CHANGE** row (`rememberPageLabel`, after **VIEW**, never on ALL) that does, and the remembered page is marked with a small square after the title whenever it's on screen and after its row in the pages list (the same one MANAGE BOX uses; kept when your own `draw` calls `defaultDraw`). `Screen.drawTitleMark(list)`/`Screen.drawRowMark(list, value)` draw that square yourself.
- `build(game, pageId, env)` -- returns `rows, listOpts, mons`. `rows` are list rows (`{ label, right, value, ... }`); `value` is what every other callback receives as `row`, untouched (an index, an id or the raw data -- your choice). A row with `inert = true` shows but can't be picked. `mons` is an optional array parallel to `rows` (`false` where there is none) that adds level icons next to Pokémon names; with `heldItemMarks = true` (on the container, or `opts.heldItemMarks`) it also draws a held-item mark.
- `dynamicFooter(game, pageId, row, nextLabel, env)`, `draw(game, pageId, list, defaultDraw, env)` -- footer text for the highlighted row, and custom drawing (call `defaultDraw()` to keep the default).
- **A** on a row opens a menu, in this order: `transferLabel` (default `TRANSFER`), `MOVE`, `removeLabel` (default `REMOVE`), then your `onAction` rows, then `CANCEL` (added when missing). `onAction` is an array of `{ label, keepOpen, visible, onSelect }` (`visible(game, pageId, row, env)`; `onSelect(game, pageId, row, rebuild, list, env)`), never a function -- a container that needs full control uses the function form of `entry.screen`.
- **TRANSFER is the default way to move a row between containers**: a container that defines `withdraw` (and a destination that defines `deposit`) gets it generated, so a third-party storage needs no `TO <label>` rows of its own. A container that builds its own `onAction` and still wants that shape (e.g. to ask a quantity first) can group its rows with `Screen.transferGroup(targets)` (`targets`: `{ label, visible, onSelect }` as in `onAction`): no row when none is visible, a direct run with one, a `TO <label>` submenu with two or more.
- `withdraw(game, pageId, row, destContainerId, env)` / `deposit(game, pageId, row, sourceContainerId, env)` -- take `row` out of this container / put it in. `destContainerId` is `nil` for REMOVE. A container is offered as a TRANSFER destination only if the current one defines `withdraw` and it defines `deposit`. `canWithdraw`/`canDeposit` (below) exclude it right now.
- `removeLabel`, `transferLabel`, `onStart` -- either a function `onStart(game, pageId, defaultStartRows, rebuild, list, env)` with full control, or an array of `{ label, keepOpen, visible, onSelect }` appended after the default rows (`TRANSFER`/`PAGES` when their own `canX` is on), same row shape and argument wrapping as `onAction`: `visible(game, pageId, env)`, `onSelect(game, pageId, rebuild, list, env)` (no `row` -- START isn't per-row).
- `onMove(game, fromPageId, fromIndex, toPageId, toIndex, env)` -- **MOVE** reorders in place, one adjacent swap per press, and left/right carries the row to the end of the previous/next page when `canRearrangeBetweenPages` is on. It is only visual until **A** confirms: then `onMove` is called once with the original and the final position and does the real reordering (a grid's Up/Down swap is the exception, below). **B** cancels without calling it.
- **Every `canX` field is a plain boolean or a function**, called with whatever args are listed for it (`game` first, `env` last, same as every other callback here) -- a function that only cares about some of them (e.g. a page-level question, ignoring `row`) just ignores the rest. Two families, by what an *unset* field means:
  - **Opt-in feature gates** -- unset means **off**: `canRearrange(game, pageId, row, env)` (adds **MOVE**; `row` is the current row when checking one specific row, `nil` when checking whether the page supports it at all -- an item's pocket is fixed, unlike a mon's box, so it can gate `false` while the aggregate **ALL** page is showing), `canRemove(game, pageId, row, env)` (adds `removeLabel`/**REMOVE**, still needs `withdraw` and `canWithdraw` to actually show), `canTransfer(game, pageId, env)` (adds the bulk `transferLabel`/**TRANSFER** to **START**, moving the whole current page with a confirmation), `canRearrangeBetweenPages(game, pageId, env)` (requires `canRearrange`, `getPages`), `canListPages(game, pageId, env)` (below).
  - **Exclusion filters over a capability that already exists structurally** -- unset means **allowed**, only an explicit `false` excludes: `canWithdraw(game, pageId, row, env)`, `canDeposit(game, pageId, row, sourceContainerId, env)`. TRANSFER collapses like the Bank's own menus: no row with zero destinations, a direct move with one, a `TO <label>` submenu with two or more. Because the rules receive the other container's id, a rule such as "only check legality when going from `bank` to `party`" needs no special case.
- **`canListPages`** (opt-in, off by default) adds a **PAGES** row (`listPagesLabel`, default `"PAGES"`) to **START** for any container with `getPages`; suppressed with 0 or 1 pages. It opens a list of every page (**ALL** first when `includeAllPage` is on) titled `listPagesLabel`, with a cursor/total counter by the title and, on each page's row, how many rows it holds (non-`inert` ones; `count/slots` when the page has `slots`, below). The cursor starts on the page on screen. Every other container of the screen with its own pages list is in the same list too (**SELECT** switches between them, each titled by its `label` then) -- the Bank's MANAGE BOX is exactly this, over BANK and PC. **A** on a page opens a menu: **MOVE** (below), **VIEW** (shows that container on that page -- the same `onPageChange`/`setRememberedPage` hooks left/right fire -- and closes the list), then `listPagesActions` (same row shape as `onAction`: `{ label, keepOpen, visible, onSelect }`, with `visible(game, pageId, env)` and `onSelect(game, pageId, rebuild, list, env)` getting the chosen page's id; `rebuild()` refreshes both the pages list and the screen behind it, `list` is the pages list, `env` the screen's own), then **CANCEL**. **B** goes back.
- **`canRearrangePages(game, pageId, env)`** (opt-in gate, `pageId` is `nil` for the list-level check) + **`onMovePage(game, pageId, fromIndex, toIndex, env)`** add **MOVE** to that menu: the pages reorder like any MOVE (Up/Down, **A** confirms, **B** cancels) and `onMovePage` is called once with the moved page's id and its old/new position among the **real** pages (ALL never counts). No `onMovePage`, no MOVE. **ALL** can't be moved, and no page can pass it -- the same rule MOVE follows everywhere: a row can't be pushed aside by one being moved if `canRearrange` refuses that row itself.
- **`slots`** (number or `function(game, pageId, env)`, optional) -- a page's capacity. It shows in the pages list (`count/slots`), a full page is never offered as a TRANSFER destination (and a bulk TRANSFER into it stops once it fills, counting the rest as refused), and MOVE never carries a row into a full page. Never applies to ALL. Your own `deposit`/`onMove` are still what actually enforce it on your data.
- **`canOverflow(game, pageId, env)`** (opt-in gate, boolean or function; `pageId` is the page on screen) -- what a TRANSFER into this container does once the page on screen is full: off (default), it's refused (a bulk TRANSFER counts the rest as refused, and a full container isn't offered as a destination); on, the row goes to the next page with room, in page order and wrapping around (never ALL), and only a container with every page full is refused. Your `deposit` gets that page's id, and `env.pageOf(<this container>)` returns it for the length of the move (so a `withdraw` that places the row itself lands it there too). The Bank's BANK and PC boxes have it on.
- **`emptySlots`** (opt-in gate `function(game, pageId, env)` or boolean, needs `slots`) pads the page up to `slots` with `inert` rows labeled `emptySlotLabel` (default `<EMPTY SLOT>` on FireRed, `-----` on Gen 1/2, whose font has no `<`/`>`). They can't be picked, don't count, and MOVE keeps the moved row above them (carried into a page, it takes the first one's place).
- **`columns`** (number or `function(game, pageId, env)`, default `1`) -- more than `1` shows the page as a **grid** of square cells instead of a list (floored, and capped so no cell is under 16 px: 9 columns at most on Gen 1/2). Cells fill the list's own area (the whole screen between the title and the footer on Gen 1/2, the list window under its title line on FireRed), a row at a time; the list scrolls by whole rows (`list.scroll` still counts rows of `rows`, always a multiple of `columns`). Controls: Up/Down move a row (Down reaches a partial last row's last cell), Left/Right a cell; at a row's first/last column (or the last cell, or on an empty page) Left/Right turn the page instead, landing on the same row's last/first column of the new page (clamped to what it holds). Without `getPages` the row's edges stop there. Holding a direction repeats it. In **MOVE**, Left/Right swap with the neighbouring cell, and at a row's edge carry the row to the adjacent page when `canRearrangeBetweenPages` is on (Left: to the end of the previous page, Right: to the start of the next one); Up/Down swap it with the cell above/below (Down reaches a partial last row's last cell; never `emptySlots` padding, but an `inert` row can be swapped). A swap isn't one remove/insert, so after one `onMove` is called once per step when **A** confirms, in order: what the row moved before the swap, the row to the other cell, and the displaced row back to where the moving one was (plus the rest of the move afterwards) -- each call still a plain remove/insert, so replaying them gives exactly what the grid showed. Without a vertical swap it stays a single call, and **B** still cancels without calling it. A grid ignores the level text (`mons`), the held-item mark next to the label and `listOpts.itemBox`/`messageBox` (the footer shows where a full-screen list has it); `heldItemMarks` draws its mark in the cell's corner instead. Title, counter, `draw`/`defaultDraw`, `dynamicFooter`, `inert` rows and every row menu work as in a list. The Gen 1 modern UI keeps showing it as a list.
- **`icon(game, pageId, row, env)`** (optional) -- what a grid cell shows: an image (or `image, quad`), drawn scaled to the cell and centered, or a function `draw(x, y, size)` that draws itself inside the `size`-pixel square at `x, y`. It runs once per rebuild, inside `pcall`; `nil` or an error shows the row's `label`, cut to the cell (an `inert` row shows nothing). Ignored by a plain list.
- **Pages list as a grid** (all optional, only read when the container has `canListPages`): `listPagesColumns` (number or `function(game, env)`, same flooring/capping as `columns`; `> 1` shows the pages list of **START > PAGES** as a grid of cells), `listPagesIcon(game, pageId, env)` (what a cell shows, same return as `icon`; by default the page's position number, plus a small square on the remembered page), `listPagesOnStart` (array of `{ label, keepOpen, visible, onSelect }` for **START** in that list, with `visible(game, pageId, env)` and `onSelect(game, pageId, rebuild, list, env)` -- where a view toggle goes; `pageId` is always `nil` there) and `listPagesFooter` (`true` shows, for the highlighted page, its label on the first footer line with its `count/slots` flush right, and on the second the **SELECT**/**A**/**START** hints). Without them the pages list is the plain list it always was. `MultiArray`/`MultiMap`/`Map`/`Array` `.entry()` and `.subscreen()` pass all four through from `config`, like `listPagesLabel`.
- Picker only: `pickLabel` (default `PICK`); `onAction` may also be a function `onAction(game, pageId, row, choose, env)` (`choose()` runs `opts.onChoose`) or an array (a `pickLabel` row first); without it **A** calls `opts.onChoose(row, { containerId, pageId, index })` directly. `choosePage = true` makes **A** pick the whole page instead: `opts.onChoose(nil, { containerId, pageId })`.

**`env`** is a handle owned by that one open of the screen: `env.game`, `env.data` (a scratch table, seeded from `opts.data`), `env.pageOf(containerId)` (the page each container shows right now) and `env.screen` (the finished screen, with `refresh` and `jumpTo`).

`AmountBox.new(game, opts)` (`opts = { max, wallet, bank, prefix, walletLabel, bankLabel, title, screenId, onDone(amount or nil) }`, exported on `bank.exports.AmountBox` and provided by `Widgets`) and `askQuantity(game, list, count, cb, text)` are exported for a mod that wants the same amount and quantity prompts.

The four public **Pickers** below are built on `Screen.pickerScreen` and did not change: the same options and the same `{ refresh, setFooter, close }` handle.

## Events

Every deposit, withdraw, release, teach and item/money transfer -- through this mod's own UI or through the exports above -- fires one of:

- `mod.vrm_pokemon_bank.pokemon_deposited` -- `{ box, index, mon }`
- `mod.vrm_pokemon_bank.pokemon_withdrawn` -- `{ box, index, mon }`
- `mod.vrm_pokemon_bank.pokemon_released` -- `{ box, index, mon }` (`box` is `nil` for a TIME CAPSULE release -- it has none)
- `mod.vrm_pokemon_bank.item_deposited` -- `{ id, qty }`
- `mod.vrm_pokemon_bank.item_withdrawn` -- `{ id, qty }`
- `mod.vrm_pokemon_bank.item_tossed` -- `{ id, qty }`
- `mod.vrm_pokemon_bank.move_deposited` -- `{ id, qty }`
- `mod.vrm_pokemon_bank.move_withdrawn` -- `{ id, qty }`
- `mod.vrm_pokemon_bank.move_tossed` -- `{ id, qty }`
- `mod.vrm_pokemon_bank.move_taught` -- `{ id, mon }`
- `mod.vrm_pokemon_bank.money_deposited` -- `{ amount }`
- `mod.vrm_pokemon_bank.money_withdrawn` -- `{ amount }`
- `mod.vrm_pokemon_bank.link_completed` -- `{ sent, received, entries }`, once a LINK exchange lands in the Bank (after both sides' second CONFIRM). `sent`/`received` are each `{ pokemon, timeCapsule, items, moves, money, coins, ext }` -- `pokemon`/`timeCapsule` counts (`timeCapsule` is always `0`: the TIME CAPSULE stays out of LINK), `items`/`moves` summed quantities, `money`/`coins` totals, `ext` the other storages' own as `{ [storageId] = { [entryKey] = count } }` (only those that moved something); none of them count the LOST rows. `entries` is `{ sent, received }`, each `{ [storageId] = { [entryKey] = { count, qty } } }` for every entry (the Bank's own included) that moved something, LOST rows included: `count` operations as the **Basic counters** count them and `qty` their units.
- `mod.vrm_pokemon_bank.link_cancelled` -- `{}`, whenever a LINK session ends any other way (CANCEL, a version mismatch, linking to yourself, a dropped connection) and everything staged to send was handed back.

- `mod.vrm_pokemon_bank.storage_action` -- `{ id, key, action, amount, value }`, for every action on any entry of any storage, the Bank's own included (right after its own event above, when it has one; TIME CAPSULE deposits and withdrawals only fire this one): `action` is `"deposit"`, `"withdraw"`, `"remove"` or `"use"`, `amount` the units or elements, `value` the POKéMON or the id involved when there is one. LINK never fires it.

`mod.events:on("mod.vrm_pokemon_bank.pokemon_deposited", function(payload) ... end)` subscribes the usual way. Remember `box`/`index` in a payload are only a snapshot -- see **Box numbering** above.
